Step 1

Craftsman’s Demonstration

In Phase 1 the Craftsman demonstrates on a different problem than the apprentice will solve, and narrates its thinking aloud.

The Craftsman speaks

“Watch me decide something. I want a function that tells me whether a number is positive, negative, or zero. Notice there are exactly three outcomes — so before I type anything, I promise myself every number will land in one and only one of them. Let me think out loud.

First branch: is it positive? n > 0. Second: is it negative? n < 0. What’s left? Only zero. So the last branch isn’t a test at all — it’s everything that survived the first two. In Shoddy I write that with If … Then … Else, and I lean on Else to catch the leftover so I can’t forget it.”

Def SignWord(n As Number) As String
    If n > 0 Then
        "POSITIVE"
    Else
        If n < 0 Then
            "NEGATIVE"
        Else
            "ZERO"

The Craftsman speaks

“Two things to notice, apprentice. One: in Shoddy, whatever a branch ends up with is the answer it hands back. I don’t need a special ‘give this back’ command — I just write the word I want, like &quot;POSITIVE&quot;, on its own line, and that’s what comes out. Two: I put a second If inside the first Else — a decision inside a decision. That’s honest, and it works, but watch how it starts to look like a staircase leaning to the right. It gets harder to read fast when there are lots of choices. Hold that thought — you’ll feel that awkwardness yourself in a minute, and then I’ll show you the tool that fixes it.”

“Three inputs, three homes, no overlaps, nothing left over. That is what ‘enumerating cases’ means. I did it on paper before I trusted the machine.”

Step 2

The Challenge

Now the apprentice holds the pen.

Create a new file grade.shoddy and write one function:

Def LetterGrade(score As Number) As String

It takes a test score (a Number from 0 to 100) and gives back a letter grade as a String (a piece of text):

ScoreGrade
90 and above"A"
80 to 89"B"
70 to 79"C"
60 to 69"D"
below 60"F"

Then add a Main that prints the grade for a few scores so you can run it:

Def Main()
    Print(LetterGrade(95))
    Print(LetterGrade(83))
    Print(LetterGrade(72))
    Print(LetterGrade(60))
    Print(LetterGrade(41))

Constraints (this is Phase 1 — the friction is the point):

  • Write every line yourself. The Craftsman will not give you Shoddy code.
  • You may use nested If … Then … Else (like the demonstration) or reach for Select Case if you want to discover it — your choice. Both are fair.
  • Do not run it yet. Step 3 comes first.
Step 3

Predict Before You Run

Never run code without a guess first.

Before pressing ▶, write your answers down — on paper, or as a note at the bottom of your file (start the line with Rem, which tells Shoddy ‘this is a note for humans, ignore it’):

  1. For each of the five Print calls, what exact string do you expect?
  2. Here’s the sharp one: what does your code give back for a score of exactly 90? Walk through your Ifs or Cases by hand, in order, and point to the first one that catches it.
  3. And for exactly 89? For exactly 80?
  4. What would your code do for 100? For 0? Are those inside your five cases, or did you assume them?
GateWrite the predictions now. Do not scroll to Step 5 until you have. The boundary values — 90, 89, 80, 60 — are exactly where conditional bugs hide.
Step 4

Productive Struggle

The Craftsman asks questions and only escalates hints when the apprentice is genuinely stuck — it never says ‘wrong.’

If the apprentice hasn’t started:

  • “You did this on paper for SignWord — three outcomes, three homes. How many homes does a grade have? Start by writing the first test you’re most sure about.”

If the apprentice wrote overlapping conditions (tested score > 80 for B without ruling out A first):

  • “Trace a score of 95 through your branches by hand. Which branch catches it first? Is that the one you wanted?”
  • (still stuck) “Your branches are checked top to bottom, and the first match wins. What does that tell you about the order you should put 90 and 80 in?”

If the apprentice hit the classic boundary bug (used > where they needed >=, so 90 falls through to &quot;B&quot;):

  • “You predicted 90 in Step 3. Run only that value in your head again, slowly. Does 90 > 90?”
  • (still stuck) “There’s a difference between ‘greater than’ and ‘greater than or equal to.’ Which one does ‘ninety and above’ mean?”

If the apprentice tried to treat a Boolean as a number (wrote something like If (score >= 90) + (score >= 80) Then):

  • “In Shoddy, score >= 90 produces a Boolean — True or False. Your docs say a Boolean is never a number. Can you add two of them? What is the language telling you when it complains?”

If the apprentice’s nested Ifs have become a staircase they can’t read:

  • “You’ve nested four Ifs and it’s hard to see. You’re feeling exactly the pain I hinted at. There’s a Shoddy form built for ‘match this one value against many cases.’ It starts with the words Select Case. Open QUICKREF and look at what Case Is >= 90 and Case 70 To 89 do — then decide if it’s cleaner.”
ContractThe Craftsman withholds the fix at every tier until the apprentice has taken one more real attempt. The struggle is where the learning is stored.
Step 5

Run & Validate

Execute, then compare to your prediction.

Press ▶ (or Ctrl+Shift+B). You should see five lines in the integrated terminal. Now the real work: compare each line to your Step 3 prediction.

  • All five match? Good — but you’re not done. You only tested five interior values. Add these boundary lines to Main and run again:
    Print(LetterGrade(90))    Rem you predicted: A
    Print(LetterGrade(89))    Rem you predicted: B
    Print(LetterGrade(80))    Rem you predicted: B
    Print(LetterGrade(60))    Rem you predicted: D
  • A line doesn’t match your prediction? This is the lesson, not a failure. A mismatch means either your code is wrong or your understanding was wrong — and finding out which is the whole skill. Go back to the branch that produced the surprise and trace that one value by hand.
PerchIf you get ERROR (line N): …, Shoddy points you at the exact line. Read the message, go to that line. Want to watch it decide? Press F5 to open the perch (the debugger). Set a breakpoint on your first If line, step with F10, and watch the score binding in the Locals panel as each branch is tested. Seeing 90 walk past a > test and fall into the wrong branch is worth a thousand words.

A reference solution exists — but you don’t get it until after you’ve made yours run. In fact Shoddy gives you two clean idioms, and the difference between them is itself a lesson:

Idiom A — explicit ranges (To)

Each case names its exact interval, so correctness doesn’t depend on order:

Def LetterGrade(score As Number) As String
    Select Case score
        Case Is >= 90
            "A"
        Case 80 To 89
            "B"
        Case 70 To 79
            "C"
        Case 60 To 69
            "D"
        Case Else
            "F"

Idiom B — cascading >=

This is how Shoddy’s own gradebook.shoddy does it. Fewer characters, but it only works because the first matching case wins and the cases run high-to-low:

Def LetterGrade(score As Number) As String
    Select Case score
        Case >= 90
            "A"
        Case >= 80
            "B"
        Case >= 70
            "C"
        Case >= 60
            "D"
        Case Else
            "F"

Either way, Select Case reads as a simple top-to-bottom list — no leaning staircase. Shoddy looks at score just once, checks it against each Case in order, and Case Else at the bottom is the safety net that catches anything the earlier cases missed, so no score is ever left without an answer.

ThinkThe critical-thinking question the Craftsman will ask: what happens to Idiom B if you accidentally reorder the cases so >= 80 comes first? (Answer: every score of 90+ silently becomes a "B". Idiom A survives the reorder; Idiom B does not. Neither is ‘better’ — but a craftsman knows which fragility they’re signing up for.)
Step 6

Craftsman’s Critique

A craftsman inspects the joinery — naming what’s sound, what’s fragile, and why.

SoundSound. “You put >= 90 first. That’s not luck — ordering top-to-bottom so the strongest condition wins is exactly right, and most beginners get it backwards.” And: “You predicted the 90 boundary in Step 3 and it caught your > bug before the computer did. That instinct is the entire point of this apprenticeship.”
FragileFragile — the silent gap. “What does LetterGrade(105) give back? What about LetterGrade(-3)? You planned for scores of 0 to 100, but a Number can be anything. Right now your code quietly answers "A" for 105. Is that what you meant? Or should an out-of-range score stop the program with an Error message instead? A craftsman decides this on purpose — they don’t leave it to accident.”
FragileFragile — the nested-If version (if that’s what you wrote). “It works, and working matters. But read it aloud — four levels deep. In six months, could you add a +/- modifier without breaking it? Compare it to the Select Case version. Same behavior, a quarter of the reading effort. Correctness and clarity are two separate quality bars, and you owe the reader both.”
StandardThe craftsman’s standard: working code is the floor, not the ceiling. Sound joinery is code the next person — including future you — can trust at a glance.
Step 7

Reflection Retro

The apprentice does the talking; the Craftsman only prompts.

  1. Where did your prediction and the result disagree? What did that mismatch teach you that a passing test never could have?
  2. Did you reach for Select Case, or discover it only when the nested Ifs got painful? The Craftsman let you feel that pain on purpose — why do you think that is?
  3. The boundary bug (> vs >=): if you hit it, what will make you check the ‘or equal to’ edge first next time, before running?
  4. Compare structures: your first working version vs. the reference. What would you change now, knowing both — and is ‘it already works’ a good enough reason not to?
Step 8

Critical-Thinking Takeaway

One durable principle.

PrincipleEnumerate every case, then go hunt the boundaries. A conditional is only correct when every possible input has exactly one home — and the bugs almost always live on the line where two branches meet (90 vs 89, 80 vs 79).

You will use this exact instinct in Phase 4, when the Craftsman writes a conditional for you and hands it over looking perfectly reasonable. The plausible-but-wrong grade function — the one that quietly sends every 90 to a "B" — is precisely the bug you now know how to catch, because today you built it, predicted it, and fixed it with your own hands. That is why you write it manually first: so that later you can judge it.
