Doing Things Again

Repeat an action — the Shoddy way, with no loops — by describing ‘for every item’ instead of counting steps.

Durable takeaway: You rarely need to say ‘do step 1, then step 2, then step 3.’ It’s clearer and safer to say ‘for every item in this group, do this.’ Describe the whole job, not each footstep.
Phase1 — Manual Craft (the apprentice writes 100% of the code; the Craftsman writes no Shoddy)
PrerequisitesLessons 1–3
New Shoddy conceptsRange(a, b) (a list of numbers from a to b); Each(list, action) (do something for every item); Times(n, action) (do something n times); the idea of a list

Step 1

Craftsman’s Demonstration

The Craftsman models the idea on its own example.

The Craftsman speaks

“In a lot of languages, to print the numbers 1 through 5 you’d write a ‘loop’ with a counter that ticks up: 1, 2, 3… and you’d have to manage that counter carefully or you’d get bugs. Shoddy doesn’t work that way, and honestly it’s simpler. Watch:”

Def Main()
    Each(Range(1, 5), Fn(n) => Print(n))

The Craftsman speaks

“Let me take that apart from the inside out.

Range(1, 5) builds a list — a group of values in order. This one is 1, 2, 3, 4, 5. A list is just ‘several things, lined up.’

Each(...) means ‘for every item in this list, do this action.’ It walks through the list for me. I never manage a counter — there’s no counter to get wrong.

Fn(n) => Print(n) is the action. Read it as: ‘given one item, which I’ll call n, print n.’ The Fn(n) => part just names the item so I can talk about it. Don’t worry about the deep details of Fn yet — we give it a whole lesson later. For now: it’s how I say what to do with each item.

So the whole line reads, in plain English: ‘for each number n in 1 through 5, print n.’ That’s it. No counter, no off-by-one mistakes.”

A second demonstration — Times, for plain repetition

Def Main()
    Times(3, Fn(i) => Print("KNOCK"))

The Craftsman speaks

“Times(3, ...) just does the action 3 times. Here it prints KNOCK three times. Use Times when you only care how many times, not which item.”

Step 2

The Challenge

Now the apprentice holds the pen.

Make a file countdown.shoddy. Two tasks in one Main:

  1. Print the numbers 1 through 10, each on its own line.
  2. Then print the line BLAST OFF! exactly once.

Constraints:

  • Use Range and Each for the counting part.
  • Do not write ten separate Print lines — that defeats the purpose. Describe the whole job in one instruction.
StretchStretch (optional): instead of 1 through 10, print 10 down to 1 (a real countdown). Think about what Range gives you and how you might flip it. If you get stuck, that’s a great Step 4 question.
Step 3

Predict Before You Run

Say what you think will happen, first.

Write down first:

  1. How many lines total will your program print? (Count carefully — this is the classic place to be off by one.)
  2. What will the very first line be? The very last number line? Will BLAST OFF! come before or after the numbers?
  3. If you used Range(1, 10), does the 10 get included, or does it stop at 9? State your belief, then test it.
Step 4

Productive Struggle

Questions, never answers.

If you wrote ten Print lines:

  • “It works, but it’s exactly what Each exists to prevent. If the task changed to 1 through 100, would you write a hundred lines? How could you describe ‘every number from 1 to 10’ in one instruction?”

If BLAST OFF! printed ten times, or in the wrong place:

  • “Is BLAST OFF! supposed to happen for every number, or just once at the end? So should it be inside the Each action, or on its own line after it? Where you put a line decides when it runs.”

If you’re unsure whether Range(1, 10) includes 10:

  • “Don’t guess and move on — prove it. Print Range(1, 10) all by itself and look. What’s the last number? Now you know instead of hoping.”

For the stretch (counting down):

  • “Range counts upward. If you have the list 1..10 going up, is there a word that flips a list around? Peek at the reference for Reverse. What would Reverse(Range(1, 10)) give you?”
Step 5

Run & Validate

Execute, then compare to your prediction.

Run it. Compare to your prediction:

  • Line count: did you get exactly 11 lines (ten numbers + one BLAST OFF!)? If you got 20, or 10, the bug is where you put BLAST OFF!.
  • The boundary: did 10 actually appear? This is the same ‘check the boundary’ instinct from Lesson 3, showing up again — it will show up in every lesson, because boundaries are where bugs live.

A correct shape (compare after yours runs):

Def Main()
    Each(Range(1, 10), Fn(n) => Print(n))
    Print("BLAST OFF!")
Step 6

Craftsman’s Critique

A craftsman inspects the joinery.

SoundSound. “You described the whole job — ‘print every number from 1 to 10’ — in one line, and put BLAST OFF! outside the repetition so it happens once. You’re already thinking in terms of ‘the whole group,’ which is exactly the Shoddy mindset.”
FragileFragile. “Did you verify that Range includes both ends, or did you assume it? An assumption that happens to be right is still a habit that will eventually bite you. Prove the boundary every time.”
Step 7

Reflection Retro

The apprentice does the talking.

  1. Compare the one-line Each version to imagining ten separate Print lines. Beyond ‘less typing,’ what makes the Each version safer?
  2. You never managed a counter. Did you miss it, or was it a relief? What kind of bug did its absence make impossible?
  3. If you did the countdown stretch: how did you figure out how to reverse the order? What did you try first?
Step 8

Critical-Thinking Takeaway

One durable principle.

PrincipleDescribe the whole job, not each footstep. ‘For every item in this group, do this’ is clearer, shorter, and safer than counting steps by hand — and it’s the exact habit you’ll use later to tell the Craftsman what to build. Learning to describe what you want is the whole game.
