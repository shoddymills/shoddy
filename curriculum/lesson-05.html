Building Your Own Words

Write your own reusable commands — functions — by breaking a big job into small, named pieces.

Durable takeaway: A function is a word you teach the computer. Once you name a small job and get it right, you never have to think about its insides again — you just use its name. Good names hide hard work behind a simple label.
Phase1 — Manual Craft (the apprentice writes 100% of the code; the Craftsman writes no Shoddy)
PrerequisitesLessons 1–4
New Shoddy conceptsDef Name(param As Type) As ReturnType — writing your own reusable command (a function); calling your own function; how a function gives back an answer
Thinking skillBreaking one big problem into small, named pieces you can build and test on their own
Time40–50 minutes
Step 1

Craftsman’s Demonstration

The Craftsman models the idea on its own example.

The Craftsman speaks

“You’ve been using words like Print and Range that Shoddy came with. Now you’ll teach the computer your own words. A word you define is called a function. Watch me build one:”

Def Double(n As Number) As Number
    n * 2

Def Main()
    Print(Double(5))
    Print(Double(20))

The Craftsman speaks

“The first block defines the word Double. Let me read the top line piece by piece:

  • Def Double — ‘I’m defining a word called Double.’
  • (n As Number) — ‘it needs one thing to work with, a Number, and inside this word I’ll call that thing n.’ The n is called a parameter — a stand-in for whatever value someone hands in.
  • As Number at the end — ‘the answer this word gives back is a Number.’

The Craftsman speaks

The indented line, n * 2, is the work. And here’s the Shoddy rule you met back in Lesson 1’s world: whatever the function ends up with is the answer it gives back. There’s no special ‘return this’ command — I just write n * 2, and that’s what comes out.

Down in Main, I call the word: Double(5). Shoddy takes my 5, slots it in wherever n appears, computes 5 * 2, and hands back 10. Then Double(20) gives 40. I taught the computer a word, and now I can use it as many times as I like without rewriting the work.”

Why this matters — a second, tiny demonstration

Def GreetLine(who As String) As String
    "WELCOME, " & who & "!"

Def Main()
    Print(GreetLine("ADA"))
    Print(GreetLine("LIN"))

The Craftsman speaks

“See how Main stays short and readable? All the fiddly text-gluing lives inside GreetLine. Once I trust GreetLine, I stop thinking about the & and the spaces — I just say the word. That’s the real power: a good function lets you forget how, and only remember what.”

Step 2

The Challenge

Now the apprentice holds the pen.

Make a file shapes.shoddy. Write two functions of your own, then use them in Main:

  1. Def RectangleArea(width As Number, height As Number) As Number — gives back the area of a rectangle (width times height). Note: this one takes two parameters — separate them with a comma.
  2. Def Describe(area As Number) As String — gives back the text "BIG" if the area is 100 or more, otherwise "SMALL". (Yes — you’ll reuse the decision skill from Lesson 3 inside a function.)

In Main, print the area of a 5×20 rectangle, then print whether it’s big or small using both of your functions together.

Step 3

Predict Before You Run

Say what you think will happen, first.

Write down first:

  1. What is RectangleArea(5, 20)? Compute it by hand.
  2. Feed that answer into Describe. Should it say BIG or SMALL? Where’s the boundary — what area is the smallest one that still counts as BIG?
  3. Can you feed one function’s answer straight into the other, like Describe(RectangleArea(5, 20))? Predict whether that works before you try it.
Step 4

Productive Struggle

Questions, never answers.

If you’re not sure how to give a function two parameters:

  • “Look at how you’d list two facts, separated by something. In Shoddy, parameters are separated by a comma: (width As Number, height As Number). Inside the function, you use both names.”

If Describe always says BIG (or always SMALL):

  • “This is the Lesson 3 boundary trap again. Walk an area of exactly 100 through your decision by hand. Did you use >= or >? Which one does ‘one hundred or more’ mean?”

If you tried to nest the calls and it errored:

  • “Read Describe(RectangleArea(5, 20)) from the inside out, like the computer does. What does RectangleArea(5, 20) become first? Then what does Describe receive? If it errored, is it a spelling or a comma, not the idea itself?”

If the apprentice asks ‘why bother with functions — couldn’t I just multiply in Main?’:

  • “You could, today, for one rectangle. But what about fifty rectangles? Or if the area rule gets more complicated next week? A named word means you fix it in one place. When would copy-pasting the math into Main start to hurt?”
Step 5

Run & Validate

Execute, then compare to your prediction.

Run it. Compare to your prediction:

  • Is the area 100? Is the description the one you predicted? If the area is 100 and it says SMALL, you’ve got the > vs >= boundary bug — the exact same bug from Lesson 3, now hiding inside a function.
  • Try Describe(RectangleArea(5, 20)) nested in one line. Same answer? Good — you just proved functions can feed each other.

A correct shape (compare after yours runs):

Def RectangleArea(width As Number, height As Number) As Number
    width * height

Def Describe(area As Number) As String
    If area >= 100 Then
        "BIG"
    Else
        "SMALL"

Def Main()
    Let a = RectangleArea(5, 20)
    Print(a)
    Print(Describe(a))
    Print(Describe(RectangleArea(5, 20)))
Step 6

Craftsman’s Critique

A craftsman inspects the joinery.

SoundSound. “You gave each job its own word. RectangleArea does one thing; Describe does one thing. Small words that each do one job clearly are the mark of good work — far better than one giant word that does everything.”
FragileFragile — your function names. “Describe is okay; Describe what? A name like SizeLabel might tell the reader more. Naming is real work — a function’s name is the promise it makes about what it does.”
Step 7

Reflection Retro

The apprentice does the talking.

  1. Explain in your own words what happens, step by step, when the computer runs Describe(RectangleArea(5, 20)).
  2. You reused the Lesson-3 decision skill inside a function. Did splitting the work into two functions make the decision easier or harder to get right? Why?
  3. Look at your two function names. If a stranger read only the names — not the code inside — would they know what each does? If not, what would you rename them to?
Step 8

Critical-Thinking Takeaway

One durable principle.

PrincipleA function is a word you teach the computer, and its name is a promise. Break a big problem into small named jobs, get each one right on its own, and then you can build with them without re-thinking their insides. This is the single most important habit for handling anything bigger than a toy — including, later, judging the functions the Craftsman writes for you.
