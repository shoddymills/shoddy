A Word That Calls Itself

Recursion — a function that uses itself — by trusting the smaller case and finding the stopping point.

Durable takeaway: To solve a big problem by recursion, answer two questions: ‘What’s the simplest case I can answer instantly?’ (the stopping point) and ‘If I could already solve a slightly smaller problem, how would that help me solve this one?’ Get those two right and the whole thing works.
Phase1 — Manual Craft (the apprentice writes 100% of the code; the Craftsman writes no Shoddy)

This is the hardest idea in Phase 1, and that’s on purpose — it’s the first time you’ll have to trust a piece of the solution you haven’t finished writing yet. Go slowly. Step 1

Craftsman’s Demonstration

The Craftsman models the idea on its own example.

The Craftsman speaks

“In Lesson 4 you repeated actions with Each. But sometimes you need to build up an answer while walking a list — like adding all the numbers together. For that, Shoddy uses recursion: a function that calls itself on a smaller piece of the problem. Watch me add up a list:”

Def MySum(xs As List Of Number) As Number
    If IsEmpty(xs) Then
        0
    Else
        First(xs) + MySum(Rest(xs))

Def Main()
    Print(MySum({ 10, 20, 30 }))

The Craftsman speaks

“First, three new list tools:

  • IsEmpty(xs) asks ‘is this list empty?’ — True or False.
  • First(xs) gives the first item. For { 10, 20, 30 } that’s 10.
  • Rest(xs) gives everything except the first item. For { 10, 20, 30 } that’s { 20, 30 }.

The Craftsman speaks

And { 10, 20, 30 } is how you write a list directly — values in curly braces, separated by commas.

Now the function itself has two parts:

  • The stopping point (the base case): if the list is empty, the sum is 0. Nothing to add. Easy, instant, no calling itself.
  • The recursive step: otherwise, the sum is First(xs) plus the sum of Rest(xs). That’s the strange, beautiful part: I use MySum inside MySum. I say: ‘give me the first number, and add it to the sum of everything else.’ I trust that MySum can handle the smaller list, even though I’m still writing it.

The Craftsman speaks

Let me trace MySum({ 10, 20, 30 }) by hand, so you see it’s not magic:

stepbecomes
110 + MySum({ 20, 30 })
210 + (20 + MySum({ 30 }))
310 + (20 + (30 + MySum({ })))
4 — empty list hits the stopping point10 + (20 + (30 + 0))
5 — add it up10 + 20 + 30 + 0 = 60

The Craftsman speaks

“Every step made the list smaller, and eventually it hit empty and stopped. That stopping point is what keeps it from going forever. Forget it, and the function calls itself endlessly.”

Step 2

The Challenge

Now the apprentice holds the pen.

Make a file listcount.shoddy. Write a recursive function:

Def Count(xs As List Of Number) As Number — gives back how many items are in the list, without using a built-in length command. You must count them yourself with recursion.

Then in Main, print Count({ 5, 5, 5, 5 }) (should be 4) and Count({ }) (should be 0).

Think about the two questions:

  • Stopping point: how many items are in an empty list?
  • Recursive step: if you could already count Rest(xs), how many more is the whole list?
Step 3

Predict Before You Run

Say what you think will happen, first.

Write down first:

  1. What should Count({ 5, 5, 5, 5 }) give back? And Count({ })?
  2. Write out the trace by hand for Count({ 5, 5 }), the way the Craftsman traced MySum. Show each step until it hits the stopping point.
  3. What do you predict happens if you forget the stopping point entirely — if there’s no IsEmpty check? (Guess; we’ll discuss it, carefully.)
Step 4

Productive Struggle

Questions, never answers.

If you don’t know where to start:

  • “Answer the easy question first: how many items in an empty list? That’s your stopping point. Write only that part first, and the Main line for Count({ }). Get that running before you touch the hard part.”

If you’re stuck on the recursive step:

  • “You don’t have to count the whole list at once. If a friend handed you the count of Rest(xs) — everything after the first item — how many more would you add for the first item itself? Just one. So the answer is 1 + Count(Rest(xs)). Why 1?”

If your program seems to run forever (or errors about depth):

  • “This is the danger the Craftsman warned about. Your function is calling itself and never stopping. What’s missing? Every recursion needs a case that does not call itself. Do you have an IsEmpty check that gives back a plain number?”
  • (still stuck) “This is Lesson 3’s boundary again, just wearing a new hat: your stopping point is a condition that draws the line between ‘keep recursing’ and ‘stop.’ Get that line wrong, or leave it out, and there’s no boundary at all — just an unbroken fall.”

If you used a built-in length word:

  • “That works, and in real code you’d use it. But the point of this lesson is to feel how recursion builds an answer. Can you count with First, Rest, and IsEmpty only? You’ll understand every length function forever after doing it once by hand.”
Step 5

Run & Validate

Execute, then compare to your prediction.

Run it. Compare to your prediction:

  • Count({ 5, 5, 5, 5 }) should be 4; Count({ }) should be 0. If the empty list gives anything other than 0, your stopping point is wrong.
  • Compare the program’s answer to the hand-trace you did in Step 3. Did the computer take the same path you did on paper? That — your paper matching the machine — is the moment recursion becomes real for you.

A correct shape (compare after yours runs):

Def Count(xs As List Of Number) As Number
    If IsEmpty(xs) Then
        0
    Else
        1 + Count(Rest(xs))

Def Main()
    Print(Count({ 5, 5, 5, 5 }))
    Print(Count({ }))
PerchWant to see it happen? Press F5 (the debugger — the perch), set a breakpoint on the Else line, and step with F10. Watch the call stack grow as Count calls Count calls Count, then unwind back to the answer. Seeing the stack build and collapse is worth more than any explanation.
Step 6

Craftsman’s Critique

A craftsman inspects the joinery.

SoundSound. “You wrote the stopping point first. That’s not just tidy — it’s the safe way to build every recursion. The stopping point is the thing that keeps it from running forever, so it deserves to be written first, not bolted on after.”
FragileFragile. “Could you explain, out loud, why the recursive step is 1 + Count(Rest(xs)) and not Count(Rest(xs)) + Count(Rest(xs))? If a line works but you can’t explain why, you don’t own it yet — and in Phase 1, you must own every line.”
Step 7

Reflection Retro

The apprentice does the talking.

  1. Recursion asks you to trust that Count works on a smaller list while you’re still writing Count. Did that feel like cheating at first? What made it finally make sense?
  2. What is the single most important part of any recursive function, the part that if you forget it, everything breaks?
  3. Compare this to Lesson 4’s Each. When would you reach for Each, and when would you need recursion instead? (Hint: does Each build up an answer, or just do an action?)
Step 8

Critical-Thinking Takeaway

One durable principle.

PrincipleEvery recursion needs a stopping point and a step toward it. Find the simplest case you can answer instantly, then assume the slightly-smaller problem is already solved and build on it. This ‘trust the smaller case’ move is one of the most powerful thinking tools in all of programming — and it’s the first time you’ve had to trust a solution before you could see all of it.
