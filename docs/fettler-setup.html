Shoddy Documentation · Fettler

Setting It Up

The clients, the doctor, the scaffolder, the exclusion list and the session hook. Read this once per machine.

Registering Fettler with an assistant makes it available. Only an exclusion makes it the route. This page is both halves, and the diagnostic that tells you which one you have. The verbs are on the Fettler page; what a tree grants is on the boundary page.

1. Install it first

Every registration below launches fettle. If it is not on PATH, nothing starts. That is not a hypothetical: every example in this documentation named a bare fettle for a while, on a machine where nothing resolved it, and the server had never once run.

Take the archive for your operating system from the release, put the binary somewhere on PATH, and check:

fettle --version

If you would rather not, fettle setup writes the absolute path of the binary you ran it with, so a registration works without an installation step. It says which it did. The portable form is better and the fallback is honest.

A distribution route considered and not taken: a dotnet tool install --global package would put it on PATH on all three platforms with one command. It needs a published NuGet feed, which is a publication decision rather than a build one, so the archive plus a documented step is what ships today.

2. fettle doctor

Two jobs in one verb: is Fettler wired into each client, and is anything on this machine letting the assistant go round it.

fettle doctor [--json] [--quiet] [--hook] [--client NAME]

It checks every client at both levels every time. --client narrows the report, never the scan, so "it looked fine" can never mean "it only looked at one".

It never writes. Diagnosis and repair are separate verbs, so a check run in a session hook can never change a machine. Repair is setup.

It never prints a secret. ~/.claude/.credentials.json sits in the same directory as files it reads. It names files and keys and never values.

What it looks for besides the registration

A client can be perfectly registered and never used, which is exactly what happened on the machine this was written for.

CheckWhat it is really looking for
2.6An allow entry pre-approving a shell command that writes files — sed -i, cp, rm, Set-Content, a redirect. Each is a route round the boundary that runs without a prompt.
2.7An allow on the built-in Read, Write or Edit. Habit reaches for the built-in first; an allow removes the last friction.
2.8Nothing denying the built-in editors. Registration makes Fettler an option; a deny makes it the route.

2.12A registered server whose command is not launchable — resolved the way the client would, through PATH and PATHEXT.
2.13A settings.local.json. Uncommitted and personal, so anything granted there never appears in review.

On deny versus allow

Which wins is the client's to decide, and Fettler is a separate process that cannot observe another program resolving its own rules. So it reports the conflict and names the fix that is correct under either precedence: remove the allow. An answer that does not depend on the assumption beats a guess at it.

3. fettle setup

fettle setup <client> | --all [--global | --local] [--dry-run] [--force] [--hooks] [--deny] [--command PATH]

  clients: claude-code · claude-desktop · vscode-copilot · github-copilot

A command rather than a .ps1 and a .sh, so there is one implementation instead of two that must be kept in step by hand — a mistake this project made once and undid.

It merges into JSON and never clobbers. These files hold other people's servers, other people's permission grants and a hook array that is already doing something. It reads, adds or updates Fettler's own key, and preserves everything else. It backs up to <file>.fettler-backup before its first write and says where that went. --dry-run prints what it would do and touches nothing.

What it will and will not correct

  • It corrects the wiring — a missing or wrong registration, a missing .fettler.json, a missing instruction block, a missing hook.
  • It does not silently correct policy. An existing allow entry is your own configuration; removing it changes how you work. Setup names the conflicting entries and leaves them.
  • It cannot correct installation. A binary that is not on PATH is not a configuration edit, and setup says so rather than writing a registration it knows will fail to launch.
  • It creates a .fettler.json, and never changes one. Creating where none exists is scaffolding; rewriting one is the escape the boundary page closes, and belongs to a person with an editor.

Re-running changes nothing the second time — for the JSON and for the marker-delimited instruction block alike. A registration that already says something different needs --force, so setup never quietly reshapes somebody else's choice.

setup is the one verb an assistant is not offered. It writes the file naming the command that launches the server, so a model holding it could point its own boundary at a different binary, or grant back the permissions the deny list removes. doctor is offered, because a model diagnosing its own wiring beats asking a person to open a terminal.

4. The exclusion list is two lists

Half one — the built-in tools. Short, closed, winnable.

Six entries, no arguments, no platform variants:

ToolWhy
Writemutation
Editmutation
NotebookEditmutation
Grepthis is what search replaces, and where the drift happens
Globthe same, for find
Readdenied, with no path-scoped exception

This works because the Fettler tools have different names (mcp__fettler__edit and so on), so denying the built-ins does not disarm the assistant — it routes it.

Read is the one people wave through, on the reasoning that reading is not the risk. It is. A blanket Read defeats containment for reads, the read permission, and hidden scopes entirely — a scope with no list is invisible to search and one call away from being read in full. The harm sits squarely inside the threat model: cancelled requirements read back as current, and a credentials file in the same directory as the configuration being examined.

Denying it is affordable only because Fettler reads everything the developer actually has — notebooks, images and PDF included. The deny and those readers are one shipment.

Half two — the shell. Long, open-ended, unwinnable as a blocklist.

A sample of what a blocklist would have to name: sed -i, cp, mv, rm, tee, dd, install, ln, truncate, patch, touch, git checkout|restore|clean|apply; and Set-Content, Add-Content, Out-File, Copy-Item, Move-Item, Remove-Item, New-Item, Rename-Item with their aliases and the cmd forms; and macOS's sed -i '', which is the same command with different syntax from the GNU form, so even a shared entry needs writing twice; and python -c, node -e, perl -pi -e, awk.

And then echo x > file defeats all of it, because > turns any command into a writer.

So do not write one. Deny the shell tools and allowlist the few commands actually needed — the build, the test runner, git status|log|diff. That is the only form of this that can be finished.

Windows has two shell tools, not one. The machine this was written for named Bash twenty-two times in its settings and PowerShell zero — while PowerShell was the shell used for essentially every command in the session. A Bash-only list would have caught none of it. The doctor checks both.

5. The session hook

fettle setup claude-code --local --hooks

Runs fettle doctor --hook at the start of each session, which is where a diagnostic will actually be read. It is silent when everything is healthy or not applicable, prints a short block naming only what is wrong otherwise, and always exits 0 — a diagnostic that can stop a session from starting will be removed within a week. It carries a timeout.

It is appended to whatever hook array is already there, never substituted for it, and it is not installed twice.

Decided against: a UserPromptSubmit hook, which would re-run this on every message for a state that changes perhaps monthly. Rejected as noise. Left as its own proposal: a PreToolUse hook intercepting the built-in editors and redirecting to Fettler, which would enforce what the deny list requests. Larger, riskier, and worth its own decision rather than being folded in here.

To remove it, delete Fettler's entry from the SessionStart array in .claude/settings.json. There is a backup beside that file from the first time setup wrote it.

6. Where to say it so it is read

Ranked by how much each actually changes behaviour.

RankWhereWhy
1The MCP instructions string and the per-verb tool descriptionsRead at the moment a tool is chosen, ships with the tool, needs setup by nobody, reaches every client at once. Ours to write.
2The SessionStart hookAutomatic, and costs one line.
3Global CLAUDE.mdWhere standing rules already live and demonstrably work.
4Repo CLAUDE.md and the grounding pageProject scope, and the canonical long form.
5permissions.denyEnforcement rather than instruction — the only one that does not rely on anything being read.
Instruction is the weak lever, and it is worth being honest about it. In the session that produced this design the assistant had extensive grounding, reached for a working directory on nearly every command anyway, and needed three corrections. Ranks 1–4 are worth doing and none is sufficient. What works is removing the need: Fettler wants no working directory now that trees are declared, and everything else that did — a build, git, a script — has a cwd-free form (git -C, an absolute path, fettle run).
