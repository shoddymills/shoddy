Shoddy Documentation

Fettler

File, search and edit tools for a model and a script. One program, two front ends, and no shell between it and the file.

Fettler performs the operations an assistant actually carries out on source files: find a file, search its contents, read it, write it, edit it, move it, copy it, delete it, and run a named build task. It is written entirely in C#, it ships from this repository, and it installs as one thing.

The project is Fettler; the command is fettle. The imperative, because fettle move a.txt b.txt reads as an instruction and fettler move does not. Both spellings are correct and neither is a typo.

Where the Name Comes From

A fettler kept the carding engines in order. Carding is the stage that combs tangled fibre into a web fit for spinning, and the engine does it with rollers wrapped in card clothing — a dense bed of fine wire teeth. Those teeth load up with matted fibre, oil and dirt, and a loaded card cards nothing. The fettler stripped them, cleaned them, set them back to their proper height and spacing, and repaired what had bent.

He made no cloth. Not a yard of it. His whole job was keeping the machines that made cloth in a state where they could — which is this tool's relationship to everything around it. Fettler compiles nothing, runs nothing, and produces no program of its own. It keeps the material in order so the machines that do produce something can.

To fettle is the plain English for exactly that: to put right, to make ready, to set in order. It survives in ordinary use in in fine fettle, so the name carries its own meaning without a glossary — which is more than can be said for most tools named after a trade.

The names not taken, so the question is not re-opened: Millwright had the right instinct against the wrong object, maintaining the machinery rather than the material it runs on. Mender was exact for the editing half and undersold the other five verbs. Overlooker was the right domain with the wrong emphasis — supervision rather than repair. Tuner was genuinely apt and hopelessly overloaded. Mungo is already taken elsewhere in this family. Card grinder, strapper and oiler are all real mill trades and all name one job, where this tool does six unrelated ones.

1. Why it exists

Today these operations reach a source tree through a shell — Git Bash on one machine, Windows PowerShell 5.1 on another — and the shell is where they break. Quoting, && versus ;, /dev/null versus NUL, here-string termination, native stderr becoming a terminating error under PowerShell 5.1: none of these are file problems, and all of them are paid on every single operation. A program that takes an argument array and answers a typed result does not have that layer at all.

2. The verbs

One verb per operation, and the CLI verb and the MCP tool name are the same word. Two vocabularies for one surface would break parity on the first day, so both front ends reach the operations through one dispatcher — which makes a capability available to a model and not to a script unwritable rather than merely forbidden.

3. The boundary

Every path lies inside a declared root, and more than one root may be declared. That is the ordinary case rather than the exotic one: an assistant working here has a repository, a sibling repository and a scratch directory, and a single root would refuse work its own harness already permits — pushing it back into the shell, which is the one outcome the whole design exists to prevent.

fettle serve --root repo=/work/shoddy --root scratch=/tmp/scratch
fettle move scratch:draft.md repo:docs/notes.md

A tree declares its own boundary. Typing two absolute roots onto every command is not something anyone does for long, and the way out that suggests itself — a small shell script per platform holding the paths and passing them through — is worse than the problem: it puts a shell back between the caller and the files, which is the thing Fettler exists to remove, and being a twin pair it has to be kept in step by hand. A file at the top of the tree says it once instead:

{
  "roots": {
    "repo": "."
  }
}

With no --root on the command line, fettle takes the nearest .fettler.json at or above the current directory. Its paths are relative to the file, never to whoever is asking — which is the whole point of it. A path read against the caller's working directory names a different tree from every directory; read against the file's own directory it names one tree from everywhere, so the same command means the same thing three levels down, and the file can be checked in.

The command line replaces the file rather than adding to it. Merging would leave a caller unable to narrow the boundary — the tree's own roots would stay open beside whatever was asked for, and "just this directory, please" would be unsayable. --config PATH names a different file; --no-config turns the search off and leaves the current directory as the root. fettle roots answers what is declared and which file declared it, which is better than learning the boundary by being refused by it.

A malformed configuration is refused, never fallen back from. Quietly reverting to the current directory would move the boundary without saying so, and usually widen it — a caller's working directory tends to sit above the root they meant — which is the one direction a containment mistake must never fail in.

Containment does not weaken for being enumerated. Every path resolves inside some root by the same rule; both ends of a move or a copy are checked; a root that does not exist is a startup failure naming it; and an operation crossing from one root to another says that it crossed, because moving a file between two trust domains is something the caller is entitled to see.

Containment is decided by walking down from the volume, not by inspecting the deepest component. Given root/a/b where a is a link out of the tree, b is not itself a link and looks perfectly contained; only resolving a on the way past catches it. Windows junctions are resolved exactly as symbolic links are — they are both reparse points, junctions are what build tooling plants, and a boundary that handles only one has a hole exactly where a tree is most likely to have one.

The known limit, stated rather than implied. Path comparison does not defend against another process replacing a component between the check and the operation that follows it. Closing that needs operating-system support Fettler does not have. The boundary is a boundary, not a defence against a hostile process sharing the root.

Arguments it will not guess at

A flag no verb knows is refused, never ignored. Ignoring one does not produce a failure, it produces a wrong answer: a flag that takes a value also swallows the argument after it, so a misspelt --gob "*.cs" eats the pattern, and the search then runs against the whole tree and reports what it found with complete confidence. This was found by typing --totally-made-up at the tool and watching it exit zero.

A pattern may arrive as bytes rather than as an argument. --pattern-file PATH and --pattern-stdin take one pattern per line, the same shape a fettle-tasks file uses. The pattern is the argument a shell is likeliest to spoil — quotes, backslashes and a leading -- all mean something to somebody before Fettler sees them — and the damage is silent, because a mangled pattern does not fail, it matches something else. This is the same argument as --with-file for edit text, in the place it turns out to matter just as much.

A byte-order mark on a stream is not content. A BOM is a fact about a file's encoding and belongs at the head of a file or nowhere, so a leading one is taken off anything read from stdin. Keeping it was wrong twice over in one afternoon: a search pattern prefixed with U+FEFF matched nothing at all, and replacement text prefixed with one spliced an invisible character into the middle of a source file. Windows PowerShell emits one whether or not it is asked to. A mark further along is left alone — there it is a zero-width no-break space somebody may have meant.

Text an edit brings in is rewritten into the file's own line endings; text already in the file is not touched. A caller composing a replacement cannot be expected to know what a file's endings are, and on Windows the shell decides for them — a PowerShell here-string is CRLF whatever the file is. Splicing that in verbatim leaves a file disagreeing with itself by exactly one line, which nothing notices until a version control system does. That happened in this repository, to Fettler's own source, and is why the rule exists.

A file that disagrees with itself says so. read reports the dominant ending and marks the file (MIXED) when more than one is present — line_ending and line_ending_mixed in the machine-readable answer. The dominant ending is still what an edit inserts with; reporting only that was what hid the stray CRLF above for two commits. Nothing is silently regularised: a mixed file read and written back unchanged is still byte-identical, mixture and all.

4. What it touches besides content

A tool that edits files is asked this by every reviewer, so the answer is on this page rather than in the source.

ThingWhat Fettler does
The executable bitpreserved by copy and move, reported by read and find, settable by exec. It is the one permission git tracks, because it is the only one meaning the same thing on both platforms. NTFS has none, so it is reported absent rather than invented.
Attributes, alternate data streams, extended attributescarried across a staged write, or the answer names what could not be. A Mark-of-the-Web or a com.apple.quarantine flag dropped by an edit is a security marker weakened as a side effect of changing text.
The Windows read-only attributeread and named in the refusal, never met as an obscure OS error. delete --force clears it explicitly.
Links and junctionsreported with their targets, and never created — creating a symbolic link on Windows needs Developer Mode or elevation, so the verb would fail confusingly on a required platform.
Modified timereported; preserved on copy only when asked. Both branches are explicit, because doing nothing is not the same on both platforms: Windows carries the time across where POSIX cp gives a new one.
Everything else about permissionsnothing. No chmod, no chown, no ACL editing. POSIX modes and Windows ACLs do not map onto one another, and an abstraction over them would be a falsehood told in a table.

5. The rules a caller has to know

RuleWhat it is
Glob* stays within one path segment; ** matches any number of whole segments including none; ? is one character and does not cross a separator. Matching is case-insensitive on every platform — both required platforms have case-insensitive filesystems, so fixing it here means a pattern behaves identically everywhere.
Exclusions.git, bin, obj, artifacts and node_modules are skipped by name, the count is reported, and --include-generated turns it off. .gitignore is deliberately not honoured: implementing its rules subtly wrong hides files while appearing to work.
Attributes never decide matchinga dotfile is an ordinary file and a Windows hidden file is an ordinary file. Both are matched normally and both are reported.
Regular expressions.NET's dialect, which is neither PCRE nor ripgrep's. Every expression runs under a bound — the non-backtracking engine where the pattern allows it, an explicit timeout where it does not — so a runaway pattern is an error rather than the end of the tool.
Encodinga byte-order mark decides and is preserved; absent one, content that decodes as UTF-8 is UTF-8; anything else is binary and is refused. No statistical guess is made, because a wrong guess corrupts a file on the way out.
Orderingresults are ordered before any limit is applied, so the same query returns the same answer in the same order and a truncated result says that it was truncated.
What runs at onceread-only operations run concurrently; operations that mutate the tree are serialized against each other; run holds neither lock, so a four-minute gate does not stall a read and can be cancelled part-way.

6. Running things

run executes only what a fettle-tasks file at the root declares, and never composes a shell command — the program is launched with its arguments as a list. The declaration format is one argument per line, so there is no quoting syntax in it to get wrong: a file that cannot express a quoting rule cannot carry a quoting bug.

build:
  pwsh
  -File
  build.ps1

gate:
  node
  scripts/gate/driver.mjs
  gate
  --resume
That file is trusted input. Containment guards paths; it does not and cannot guard the command list, which is read from a file inside the very root Fettler was pointed at. Whoever can write it chooses what a caller — a model included — can execute. This is a position, not an oversight: the alternative puts the declaration somewhere the repository's own contributors cannot change alongside the build it belongs to. Point Fettler at a tree you trust.

7. Installing it

One download, one thing on disk, and no .NET install on the target machine. Every release attaches a self-contained single-file fettle per operating system, beside the extension and sparky.

PlatformArchive
Windowsfettle-X.Y.Z-win-x64.zip
macOS, Apple siliconfettle-X.Y.Z-osx-arm64.tar.gz
macOS, Intelfettle-X.Y.Z-osx-x64.tar.gz
Linuxfettle-X.Y.Z-linux-x64.tar.gz

Unpack it somewhere on your PATH. The unix archives are tars rather than zips for a reason this tool of all things should get right: the execute bit only survives a tar, and a fettle that arrives without it does not run.

# macOS and Linux
tar -xzf fettle-X.Y.Z-osx-arm64.tar.gz -C ~/.local/bin
fettle --version

Building from source needs nothing else built first — Fettler references no other project in this repository:

cd fettler
./build.ps1 publish        # or ./build.sh publish

8. Configuring an assistant to use it

serve starts the MCP front end on stdio. It is a subcommand rather than a second executable name because selecting a front end by the name it was invoked under is a Unix convention resting on a mechanism not in ordinary use on Windows.

The contract

Client configuration formats move faster than this page does. The contract does not: launch fettle serve against the tree it may touch, and speak JSON-RPC over stdin and stdout. The roots come from that tree's .fettler.json, found from the server's own working directory; where a client offers a workspace variable, name the file with --config rather than trusting a working directory you did not choose. A second tree, or a client with no project at all, still takes --root NAME=PATH. Every form below is that one fact wearing a different set of keys, so if one has drifted, check the client's own documentation and give it the same command and arguments.

Register Fettler per workspace, not per user — the opposite of the advice on the sparky page, and for a stated reason. Sparky is a calculator and is about no project, so it belongs in the user-level file once. Fettler's roots are the project: a server registered globally would point every workspace at one repository, and the boundary would be wrong everywhere but one.

Visual Studio Code

The workspace file .vscode/mcp.json, which checks in with the repository so everyone opening the folder gets the same tools and the same roots. Command Palette → MCP: Open Workspace Configuration creates it if it is not there:

{
  "servers": {
    "fettler": {
      "type": "stdio",
      "command": "fettle",
      "args": [
        "serve",
        "--config", "${workspaceFolder}/.fettler.json"
      ]
    }
  }
}

${workspaceFolder} is what keeps the entry portable between machines — it is the one place a checked-in MCP file can name a path without naming somebody's home directory. Open the Chat view, switch to Agent mode, and the tools appear in the tool picker under fettler.

The Shoddy language extension and Fettler are unrelated and coexist happily: one gives the editor an understanding of .shoddy files, the other gives the assistant a way to change them. See the VS Code page for the extension.

The other clients

Claude Code — one command, no file to edit. Project scope is the default and is right here, for the reason above:

claude mcp add fettler -- fettle serve

It registers the same server for the terminal and the VS Code panel alike. The checked-in equivalent is .mcp.json at the project root:

{
  "mcpServers": {
    "fettler": {
      "command": "fettle",
      "args": ["serve"]
    }
  }
}

Claude Desktop — claude_desktop_config.json (%APPDATA%\Claude\ on Windows, ~/Library/Application Support/Claude/ on macOS). Absolute paths, since the desktop app has no workspace to be relative to:

{
  "mcpServers": {
    "fettler": {
      "command": "C:\\tools\\fettle.exe",
      "args": ["serve", "--config", "C:\\github\\shoddy\\.fettler.json"]
    }
  }
}

Anything else — a client that speaks MCP over stdio needs no adapter. Launch the executable, write one JSON-RPC message per line to its stdin, read one per line from its stdout. Diagnostics go to stderr and never to stdout, so nothing the server reports can corrupt the stream.

More than one root is the ordinary case. An assistant working on a repository usually also has a sibling repository and a scratch directory. Name them all in the tree's .fettler.json, or pass one --root each; either way paths are then written name:path, and with a single root they stay bare. One root refuses work the assistant's own harness already permits, and it goes back to the shell to do it — which is the outcome the whole design exists to prevent.

Making it the only route to the tree

Registering the server makes Fettler available. It does not make it used: a model with its own file tools will reach for them out of habit, which is exactly what happened the first time this tool was finished and the very next task was carried out without it. Habit is not a reason, and guidance alone does not fix it. Denying the built-in tools does.

Claude Code has a permission system, so there it is enforceable rather than requested. .claude/settings.json:

{
  "permissions": {
    "deny": [
      "Read", "Write", "Edit", "NotebookEdit",
      "Glob", "Grep",
      "Bash(rm:*)", "Bash(mv:*)", "Bash(cp:*)",
      "Bash(sed:*)", "Bash(cat:*)", "Bash(find:*)"
    ],
    "allow": ["mcp__fettler"]
  }
}

With the built-in file tools denied, every read, search and edit has to go through Fettler, and every one of them is bounded by a declared root, crash-safe on write, and all-or-nothing across a batch. The Bash entries close the side door: without them a model simply shells out to sed and the boundary is decorative.

Check the deny syntax against your version. Permission rule matching has changed across Claude Code releases, and a rule that silently fails to match is worse than no rule at all — it reads as enforcement and is not. Confirm it bites by asking the assistant to read a file and watching it be refused.

GitHub Copilot in VS Code has no permission system to deny a tool with, and the asymmetry is worth stating plainly rather than papering over. Two levers exist, neither as strong as a deny rule, so use both:

LeverWhat it is worth
The Agent mode tool picker in the Chat view — switch the built-in file tools off and leave fettler onReal while the session lasts, but a per-user toggle nobody else on the team inherits
.github/copilot-instructions.mdChecks in with the repository and is read on every request — but it is guidance, and a model can drift from it
## File work goes through Fettler

Use the `fettler` tools for every file operation: find, search, read,
write, edit, replace, move, copy, delete. Do not use the built-in file
tools, and do not shell out to `sed`, `cat`, `find` or `mv`.

Read returns a hash. Pass it back as `expect` on an edit, so an edit
against a file that changed underneath you is refused rather than
silently clobbering someone else's work.

Prefer one call to several: read takes many paths, search takes many
patterns, batch takes many operations, and replace does one
substitution across a whole glob. The expensive part of a call is the
call.

Claude Desktop, and anything else with neither lever — put the same block in CLAUDE.md or whatever that client reads as project instructions. It is the same words; only the filename changes.

That block is guidance and a model can drift from it, which is why it is the fallback rather than the mechanism. Where a permission system exists, use it.

9. What it deliberately does not do

Version control — nothing here wraps git, and mixing the two would put history-rewriting commands behind a file-editing tool. Remote or networked transport — a tool reachable over a socket is a different threat model and a different document. A trash or undo store. Binary editing. Language-aware editing, which would need a parser per language and a reason to trust it. Creating links. Setting a timestamp to a value the caller names, which is a forgery capability with no use here.
