Shoddy Documentation

Fettler

File, search and edit tools for a model and a script. One program, two front ends, and no shell between it and the file.

← PreviousThe boundarySetting it upNext →

An assistant given Fettler cannot go wandering, and everything outside the boundary is denied. Every path it touches lies inside a tree you declared. Outside is refused — not only writes, but reads, listings, and knowing a file is there at all. There is no working directory to change, no path that climbs out of a tree, and no shell to reach past it with. So it cannot drift into a sibling checkout, a vendored copy, an old branch or your home directory, read something that is not the code in front of it, and then answer from that with complete confidence.

fettlebounded file tools · no shell in between

Inside the boundary it does the work an assistant actually carries out on source files: find a file, search its contents, read it, write it, edit it, move it, copy it, delete it, and run a named build task. It is written entirely in C#, it ships from this repository, and it installs as one thing. And nothing it does touches how you work — your shell, your file explorer, your IDE and your git are exactly as they were.

The project is Fettler; the command is fettle. The imperative, because fettle move a.txt b.txt reads as an instruction and fettler move does not. Both spellings are correct and neither is a typo.

Where the Name Comes From

A fettler kept the carding engines in order. Carding is the stage that combs tangled fibre into a web fit for spinning, and the engine does it with rollers wrapped in card clothing — a dense bed of fine wire teeth. Those teeth load up with matted fibre, oil and dirt, and a loaded card cards nothing. The fettler stripped them, cleaned them, set them back to their proper height and spacing, and repaired what had bent.

He made no cloth. Not a yard of it. His whole job was keeping the machines that made cloth in a state where they could — which is this tool's relationship to everything around it. Fettler compiles nothing, runs nothing, and produces no program of its own. It keeps the material in order so the machines that do produce something can.

To fettle is the plain English for exactly that: to put right, to make ready, to set in order. It survives in ordinary use in in fine fettle, so the name carries its own meaning without a glossary — which is more than can be said for most tools named after a trade.

The names not taken, so the question is not re-opened: Millwright had the right instinct against the wrong object, maintaining the machinery rather than the material it runs on. Mender was exact for the editing half and undersold the other five verbs. Overlooker was the right domain with the wrong emphasis — supervision rather than repair. Tuner was genuinely apt and hopelessly overloaded. Mungo is already taken elsewhere in this family. Card grinder, strapper and oiler are all real mill trades and all name one job, where this tool does six unrelated ones.

1. What it buys

Three things, in the order they matter: it is faster, it is repeatable, and it is bounded.

Speed — by removing exchanges and waste, not by running faster

  • Every answer is already the next call's argument, so edits stop being refused. search hands back tree:path:line:column; read numbers every line it returns and states the file's hash. Those are exactly what edit asks for — --insert-after 412, --delete 150-151, --between 120-140, --expect HASH. Nothing has to be re-read to work out where something was, and no anchor has to be reconstructed from memory and then refused for not matching. find and search exist to feed the other verbs rather than to sit beside them, and a refused edit is the expensive failure: a whole round trip spent, and usually a second one re-reading the file to find out why.
  • The hash is what makes those numbers worth having. Line numbers from a read that has gone stale are worse than none at all, because they still point somewhere — and learning that costs the round trip the numbers were saving. Proving the file has not changed costs sixty characters rather than ten kilobytes, which is the whole reason it happens on every edit instead of on the ones somebody remembered to worry about. Reliability has the chain it closes.
  • Many calls become one. read takes several paths, search several patterns.
  • Searches skip what nobody wrote. bin, obj, .git, artifacts and node_modules are excluded by default — **/*.cs matches 196 files in this repository where 119 are wanted.
  • A four-minute build stops blocking everything else. run holds no lock, so a read answers while a gate runs, and the gate can be cancelled part-way.
  • A runaway pattern is refused, not endured. Every regular expression runs under a bound.
  • A rename across a tree is two calls, not two dozen. replace substitutes everywhere, dry run first; batch sends a whole sequence as one exchange.
  • Process start is not the cost. 37 ms warm on the development machine, against a round trip measured in seconds.
The measurement that decided the design. A model's tool call costs a round trip and a block of its context; scanning this repository's 15 MB of tracked text costs a few hundred milliseconds. The exchange is three orders of magnitude dearer than the work, so the work is not what to optimise.

Reliability — the same answer twice, on both platforms

  • A file read and written unchanged is byte-identical — encoding, line endings and trailing newline detected on read, restored on write, never normalised.
  • Edits are all-or-nothing across every file they touch, because they resolve against the files as read before anything is written.
  • The same query returns the same answer in the same order. Results are ordered before any limit is applied.
  • And the same file twice, which is the hash's job. search says which line; read gives that line a number and gives the file a hash; edit --expect hands the hash back, and the write lands only if this is still the file that was searched. Break the chain anywhere — you save in your editor, a build regenerates it, another edit gets there first — and the answer is stale (exit 6) rather than a write at a line number that has since moved. No verb here is a separate facility: the finder feeds the reader, the reader feeds the editor, and the hash is what says all three were talking about the same file.
  • Concurrent edits cannot interleave. Two edits to one file give a success and a staleness refusal, never two successes — the second one's --expect hash stopped matching the moment the first landed.
  • A write survives a crash. Writes stage and replace rather than truncate and fill.
  • No shell, anywhere. The whole quoting, &&-versus-; and stderr-is-fatal failure class has nowhere to live.
  • A script keeps its execute bit. 40 files here carry mode 100755; losing the bit breaks the macOS build far from whatever lost it.
  • An edit does not strip a security marker. A Mark-of-the-Web or a com.apple.quarantine flag survives the write, or the answer says it did not.
  • A permission error reads as a permission error. denied is the operating system; refused is Fettler.

One refactor, with the arithmetic

Rename a C# type in this repository's Fettler lane and you touch 200 occurrences across 23 files — measured, not estimated, by asking fettle search. It is the change nobody does by hand and every assistant is asked to do anyway.

The round trips are the cheap half of that. The 23 files resolve together or not at all: every one is read, checked against the hash it was read at, and every substitution located, before the first byte moves. A permission the tree does not grant, a file that changed underneath it, an anchor that no longer matches — each stops the whole batch with nothing written and the tree exactly as it was.

The writing itself cannot be promised, so it is reported instead. A full disk, or a file some other process holds open, can fail halfway through any batch, and no tool prevents that. What a tool can do is leave you knowing. This is the part that actually costs an afternoon: the built-in tools stop somewhere in the middle and say nothing about where, so the tree is half-changed and the only way to find out which half is to go and look, file by file, with the search that found them already out of date. Fettler answers it from the two ends. The dry run lists what will change, in order, before anything moves; a failed write names the file it stopped at and how many had already been written. Those two facts identify the survivors exactly rather than leaving them to be guessed — and a batch that has passed its dry run has had every reason it could refuse for already taken off the table.

Guardrails — the point of the whole thing

Fettler exists to bound what an assistant can do to your tree — and what it can see of everything else. Everything above on this page is in service of that.

Damage is the obvious half. Grounding is the half that bites quietly. A model that can wander reads whatever it finds — last year's copy of the file, a vendored dependency, a sibling project that solved the problem differently, an archived branch — and then answers from it fluently and in the right shape. A deleted file is noticed within the hour. An answer grounded in the wrong tree is noticed in review, if at all. Anything outside a declared tree is denied, so there is nowhere to wander to.
  • Every path lies inside a declared tree. Outside is refused, exit 4 — and refused identically whether or not the file exists, so a refusal cannot be used to ask what is on a disk you cannot read.
  • Write access comes only from a file a person put in the tree. --root on a command line grants list read and can never grant more, at any level, with no override.
  • execute is never a default, in any tree, including the one the configuration sits in.
  • The tool cannot write the files that say what it may do. .fettler.json and .fettler.local.json are refused by every write path at every permission level — its own outcome, governed, exit 11. Without this the permission model is decoration.
  • Nor the files that say what the assistant may do. .mcp.json, .claude/settings.json, .claude/settings.local.json and .vscode/mcp.json are refused on the same terms. A model that can edit its own deny list has no deny list, and no boundary has to be breached to reach one: a project's assistant configuration lives in the project. setup still writes them, because it uses plain file IO and resolves no path through the boundary.
  • A write that would introduce a credential is refused - its own outcome, credential, exit 12. It judges the diff, so a config already holding a key stays editable.
  • A scope can take permissions away, not only add them — and a scope with no list is not there at all as far as find and search are concerned.
  • Containment walks down from the volume, so a symbolic link or a junction planted mid-path cannot smuggle a destination out.
  • Declaring nothing is a refusal, not a fallback to the current directory — a working directory usually sits above the tree somebody meant.
  • A move between trees says that it crossed, because moving a file between two trust domains is something you are entitled to see.
  • fettle doctor reports what still goes round it — a pre-approved sed -i, an allow on a built-in editor, an instructions file that has never heard of Fettler.

2. What it does not do

The boundary binds the tool, not you. Fettler is one executable that answers when called. It is not a supervisor, a policy agent or a filesystem layer, and none of the following changes on a machine that has it installed.

Your…What Fettler does to it
shell, and everything you run in itnothing. rm, sed, git and every other command work exactly as before, on any path you like.
file explorer, editor and IDEnothing. No lock, no index, no cache, no sidecar, no metadata of its own on any file.
git history and working treenothing. Fettler wraps no version control, and deliberately never will.
machine, when it is not runningnothing. No daemon, no service, no file watcher, no startup entry, no network access at all.
configurationyou write .fettler.json in your editor, and you can change it whenever you like. The tool's refusal to write it applies to the tool, not to its author.
disk, on uninstalldelete one executable. That is the whole of it.

And deliberately outside its scope, so a later reader does not re-open the question: version control, networked transport, a trash or undo store, binary editing, language-aware editing, creating links, and setting a timestamp to a value the caller names.

3. Installing it

One download, one file on disk, no .NET runtime on the target machine. Every release attaches a self-contained single-file fettle per operating system, beside the VS Code extension and sparky.

PlatformArchive
Windowsfettle-X.Y.Z-win-x64.zip
macOS, Apple siliconfettle-X.Y.Z-osx-arm64.tar.gz
macOS, Intelfettle-X.Y.Z-osx-x64.tar.gz
Linuxfettle-X.Y.Z-linux-x64.tar.gz

The unix archives are tars because the execute bit only survives a tar. Each archive also carries NOTICE and LICENSE: the single file has PdfPig bundled in, so Apache-2.0 asks the notice to travel with the binary, and MIT asks Shoddy's own copyright notice to be in every copy.

PdfPig is in fettle and in nothing else this project ships. The mill, the machines, the VS Code extension and sparky have no PDF component and no dependency on one, direct or transitive — Fettler references no other project in the repository, so it cannot leak into them. And fettle is a separate download: installing Shoddy does not install it, and it needs none of Shoddy to run. The full statement is in THIRD-PARTY-NOTICES.md.
Getting it onto PATH is the step everything else assumes, and the step most likely to be skipped. Every registration here launches a bare fettle. If nothing resolves it the server never starts, and from the assistant's side that looks like having no file tools rather than like an error.
Windows · PowerShell

Where to put it. A per-user directory — no administrator, no other account affected.

$dir = "$env:LOCALAPPDATA\Programs\fettle"
New-Item -ItemType Directory -Force $dir | Out-Null
Expand-Archive fettle-X.Y.Z-win-x64.zip -DestinationPath $dir -Force

Unblock it if the zip came from a browser. A download carries the Mark-of-the-Web and can be refused on first run.

Get-ChildItem $dir -Recurse | Unblock-File

Put it on PATH for this account, permanently. Set the user variable, read-modify-write. Not setx, which truncates at 1024 characters and flattens the machine half of PATH into the user half.

$user = [Environment]::GetEnvironmentVariable('Path', 'User')
if ($user -notlike "*$dir*") {
    [Environment]::SetEnvironmentVariable('Path', "$user;$dir", 'User')
}

Then open a new terminal. A running shell keeps the environment it started with — the commonest reason fettle is "not on PATH" a minute after being put there.

fettle --version
fettle 2.3.0
macOS and Linux

Where to put it. ~/.local/bin if it is already on PATH; otherwise /usr/local/bin, which needs sudo.

mkdir -p ~/.local/bin
tar -xzf fettle-X.Y.Z-osx-arm64.tar.gz -C ~/.local/bin
fettle --version

If the shell cannot find it, add the directory and start a new shell:

echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.zshrc

macOS quarantines anything downloaded and refuses to run it, citing an unidentified developer. Clear the attribute on the one file:

xattr -d com.apple.quarantine ~/.local/bin/fettle

From source

Nothing else in this repository has to be built first — Fettler references no other project here:

cd fettler
./build.ps1 publish        # or ./build.sh publish

Archives land in artifacts/publish/. A unix archive cut on Windows carries no execute bit, so the ones a release attaches are always a unix runner's.

4. Wiring it to an assistant

serve starts the MCP front end on stdio — a subcommand rather than a second executable name, because selecting a front end by argv[0] rests on a symbolic link and Windows makes those awkward.

{
  "mcpServers": {
    "fettler": { "command": "fettle", "args": ["serve"] }
  }
}

No root or config flag appears there, and none can. The server learns its trees at launch from the .fettler.json in the folder it starts in, before the model has said anything, and no tool schema carries a way to name a different one.

Ask the tool: fettle doctor

fettle doctor                              # what is wired up, and what goes round it
fettle setup claude-code --local --dry-run # what would change
fettle setup claude-code --local --hooks   # change it
  • Whether Fettler is registered with each client — Claude Code, Claude Desktop, VS Code Copilot, the GitHub Copilot agent — at both the global and the repository level.
  • What still lets the boundary be gone round on this machine.
  • It never writes, never prints a secret, and reads only a compiled-in list of well-known paths.
  • Exit 0 wired, 1 warnings, 2 broken, so a script can gate on it.

The top half is the wiring, client by client and level by level; the bottom half is what would let an assistant go round the boundary anyway:

$ fettle doctor

! is serious and - is worth knowing, and every check has a number so it can be looked up. The setup page lists all eleven with what each means and how to clear it.

What setup writes

Three files, and it says which before it touches any of them. Run it with --dry-run first; it prints the same report and writes nothing.

1. The registration — .mcp.json for Claude Code, .vscode/mcp.json for VS Code, the desktop config for Claude Desktop. Note there is no root or config flag, and none is possible:

{
  "mcpServers": {
    "fettler": { "command": "fettle", "args": ["serve"] }
  }
}

2. The deny list — .claude/settings.json in the project. This is the half that makes Fettler the route rather than an option, and it works because the Fettler tools have different names (mcp__fettler__read and so on), so denying the built-ins does not disarm the assistant, it redirects it:

{
  "permissions": {
    "deny": ["Read", "Write", "Edit", "NotebookEdit", "Grep", "Glob"]
  }
}

3. The session hook, with --hooks, for Claude Code only. It runs doctor at the start of every session, so a boundary that quietly stopped working is noticed at the top of the transcript rather than three edits later:

{
  "hooks": {
    "SessionStart": [
      { "hooks": [
          { "type": "command", "command": "\"C:\\tools\\fettle\\fettle.exe\" doctor --hook", "timeout": 10 }
      ] }
    ]
  }
}
  • The hook names an absolute path, the binary you ran setup with, rather than a bare fettle — a hook that cannot launch is worse than no hook, because it fails where nobody is reading.
  • It is added once. An existing SessionStart entry mentioning doctor is left alone rather than duplicated.
  • --hooks is opt-in, because a hook runs a program at the start of every session and that is not a side effect of asking for a registration.
setup adds; it does not take away. An allow entry that contradicts the deny list is named in the report and left in place — removing somebody's configuration without asking is exactly what this design objects to. A settings.local.json is never written at all: it is personal and uncommitted.
setup is the one verb an assistant is not given, and a test asserts it stays that way. It writes the file naming the command that launches the server, so a model holding it could point its own boundary at a different binary. Scaffolding a machine is a person's act, performed once, in a terminal. doctor is offered — a model diagnosing its own wiring beats asking somebody to open a terminal for it.

Registering it makes it available; only an exclusion makes it the route. An assistant with its own file tools reaches for them out of habit, and a registered server it never calls changes nothing. The clients, both levels, the exclusion list and the session hook are on setting it up.

5. The boundary

Every path lies inside a declared tree, and more than one may be declared — a folder of code, a sibling folder and a scratch directory is the ordinary case, not the exotic one. A file at the top says it once, so nobody types a boundary onto every command:

{
  "trees": {
    "work": { "path": "." },
    "requirements": {
      "path": "../shoddy-requirements",
      "can": ["list", "read"],
      "scopes": {
        "backlog":           { "can": ["list", "read", "create", "update", "rename"] },
        "backlog/cancelled": { "can": [] }
      }
    }
  }
}

The third tree is this machine's, not the project's, so it goes in the gitignored overlay beside that file rather than into one everybody checks out:

// .fettler.local.json — gitignored, merged over the file above
{
  "trees": {
    "scratch": {
      "path": "C:/Users/you/AppData/Local/Temp/claude/<project-folder>",
      "can": ["list", "read", "create", "update", "rename", "delete"]
    }
  }
}
That third one matters more than it looks. An assistant stages its long edits — a replacement block, a generated file, a diff about to be applied — in a scratch directory the harness hands it, well outside your source. Deny the built-in Write without declaring it and both routes are shut, which surfaces at the first staging write rather than while you are setting up. No execute: it is for staging text, not for running it. fettle doctor reports the gap as 2.15.
  • Paths resolve against the file, never against the caller. Read against a working directory a relative path names a different tree from every directory; read against the file's own directory it names one tree from everywhere, so the file can be checked in.
  • The seven permissions are list read create update rename delete execute. The tree the file sits in gets all but execute; every other tree gets list read unless can says more.
  • A scope replaces what its tree grants rather than adding to it, so it can take a permission away.
  • .fettler.local.json merges over the checked-in file — one tree's configuration layered on itself, gitignored, for trees that exist only on this machine.
  • A malformed configuration is refused, never fallen back from, because a silent fallback usually widens the boundary.

How a declared path is written

Relative, forward-slashed, no drive letter. There is no formal standard for this — there is a convention, and it is git's. It is what .gitignore, Docker, npm and VS Code's own task files use, and it is the only spelling that means one thing on all three platforms.

Written asWhat happens
"path": "../shoddy-requirements"correct, and means the same on every platform
"path": "..\\shoddy-requirements"refused. Windows accepts / in every API, but on macOS and Linux a backslash is an ordinary character in a name rather than a separator — so this names a file with a backslash in it, and finds nothing
"path": "C:/work/tree"allowed; absolute, so it names one machine either way
"path": "C:\\work\\tree"allowed. An absolute path cannot travel whatever its separators are, so a Windows path in a gitignored .fettler.local.json is a person describing their own machine

Refused rather than converted, because converting would make a file legitimately called a\b unreachable on the platforms where that is a legal name. The same rule applies to a scope key and to a task's cwd.

$ fettle roots
work          /work/shoddy  (default)
              can: list read create update rename delete
requirements  /work/shoddy-requirements
              can: list read
              backlog  can: list read create update rename
              backlog/cancelled  can: nothing

declared by /work/shoddy/.fettler.json
The full permission model, and the two files this tool refuses to write, are a page of their own: the boundary. Read it before writing a .fettler.json.
The known limit, stated rather than implied. Path comparison does not defend against another process replacing a component between the check and the operation that follows it. The boundary is a boundary, not a defence against a hostile process sharing the tree.

6. Declaring tasks

run executes only what the configuration declares, and never composes a shell command:

{
  "trees": {
    "work": { "path": ".", "can": ["list", "read", "create", "update", "rename", "delete", "execute"] }
  },
  "tasks": {
    "build": { "run": "pwsh -File build.ps1" },
    "gate":  { "run": "node scripts/gate/driver.mjs gate --resume", "cwd": "." },
    "sign":  { "run": "signtool sign /f \"C:\\keys\\my cert.pfx\" bin/app.exe" }
  }
}

The command grammar, in full

  • Whitespace separates arguments. Runs of spaces and tabs are one separator.
  • A double-quoted span is one argument, or part of one; the quotes are removed. "one two" is a single argument.
  • Two double quotes inside a quoted span are one literal quote.
  • A backslash is never an escape. It is an ordinary character, so a Windows path is written once rather than doubled.
  • Nothing else is special. No single quotes, no variables, no globbing, no redirection, no &&. The string is split once, and the program is launched with the resulting list.
  • An unclosed quote is refused, not guessed at.
A task takes no arguments from its caller. run accepts a name and a timeout, and nothing else — an extra word is refused, on the command line and over MCP alike, rather than dropped. What runs is therefore exactly what the file says, every time, and a variant is a second declared task rather than a composed one. 
$ fettle run build --release
refused: no such flag: --release - try: fettle help
$ fettle run build release
refused: run takes a task name and nothing else; 'release' is extra. A task is
declared whole and takes no arguments - declare a second task for the second
thing you want run.

cwd is optional, defaults to the top of the default tree, and is checked for containment like any other path.

That configuration is trusted input. Containment guards paths; it does not and cannot guard a command list, which is read from a file inside the very tree Fettler was pointed at. Whoever can write it chooses what a caller — a model included — can execute. Point Fettler at a tree you trust.

7. When it refuses

Real transcripts. Each prints its whole answer on stdout, so no redirection is needed to read a failure.

A path outside every declared tree

$ fettle read ../secrets.txt
refused: the path is outside every declared tree; ask for the roots to see the boundary
$ echo $LASTEXITCODE
4

Climbing out with .., an absolute path elsewhere, and a link leaving the tree all land here — and all answer the same whether or not the file exists.

Writing a file that says what the tool may do

$ fettle write .fettler.json --text "{}" --overwrite
refused: .fettler.json is one of the files that tell this tool what it may do,
and it does not edit those. Change it with an editor.
The files are: .fettler.json, .fettler.local.json (.fettler.json)
$ echo $LASTEXITCODE
11

Its own outcome rather than a permission denial, because nothing is missing: no grant would have allowed it. Without the rule the escape is two commands — write a task declaration, then run what you just wrote.

A write that would put a secret on disk

$ fettle write config.json --text-file staged.json --overwrite
refused: this write would add a credential to the file: line 14 (aws-access-key-id).
The secret itself is deliberately not quoted back, because a refusal that named it
would put it in the log and the transcript. Use a reference such as ${ENV_VAR}
instead, or pass the override if this is not a credential.
$ echo $LASTEXITCODE
12

It judges what the write ADDS, not what the file contains. A configuration that already holds a key stays editable, which is the whole difference between a rule people keep and a rule people switch off. Only a secret absent from the previous content stops anything, so reformatting, reordering and editing the lines around one all still work.

The refusal never repeats what it found. A line number and a detector name, and nothing else. A message naming the secret would write it into the log, the transcript, and whatever ships those onward, which is a worse outcome than the write it was refusing.

--allow-credential is offered by the command line and by nothing else. No MCP tool carries it and a test asserts none ever will. Deciding that a high-entropy string is not a secret is a judgement about your own file, and a person makes it - the same reasoning that keeps setup out of a model's hands.

This is a safety net, not a boundary, and the difference is not a quibble. Base64 the value, split the string in two, or build it from parts, and every rule here is defeated - by accident as easily as on purpose. It stops the ordinary accident of pasting a real key into a config and writing it to disk. Anyone who believes their content has been scanned for secrets has been misled, and the two tiers are deliberately narrow so that the refusals people do get are ones they believe: issued credentials whose shape their issuer fixed, and a secret-shaped name assigned a long, high-entropy, whitespace-free value that is not a ${REFERENCE}.

Running a task in a tree that does not grant execute

$ fettle run hello
refused: 'hello' would run in a tree that does not grant execute.
Add "execute" to that tree's or scope's "can" in .fettler.json.
It is never granted by default.
$ echo $LASTEXITCODE
8

The tree holding the configuration is writable by definition, so write-by-default plus execute-by-default would be arbitrary code execution — and a scope protected from delete means nothing to a task that can run del.

A task nobody declared

$ fettle run deploy
refused: no task called 'deploy'; .fettler.json declares: hello
$ echo $LASTEXITCODE
3

A flag with no value, and a flag no verb knows

$ fettle edit f.txt --insert-after 1 --text
refused: --text needs a value, and nothing followed it - write --NAME= for a deliberately empty one
$ fettle find --gob
refused: no such flag: --gob - try: fettle help

Both answer 2. Ignoring either produces a wrong answer rather than a failure: a flag with no value would take the switch value instead and write the word true into the file.

8. The verbs

The CLI verb and the MCP tool name are the same word, and both front ends reach the operations through one dispatcher — which makes a capability available to a model and not to a script unwritable rather than merely forbidden.

VerbWhat it answers
findpaths matching a glob, with size and modified time
searchmatching lines as records — path, line, column, text — for several patterns at once
readcontent, encoding, line ending, trailing-newline state and a hash, for several paths at once — and notebooks, PDFs, images and archives. --tail N for the end of a log; --member NAME for one entry inside an archive
writethe file created or replaced
edita batch applied, or the first edit that failed
replaceone substitution everywhere it appears across a glob
new / mkdiran empty file; a directory
move / copy / deletethe operation, and what guarantee it gave
extractan archive unpacked into a declared tree — or refused whole, with nothing written
execthe executable bit, set or cleared
rootsthe declared trees, their paths, what may be done in each, and which one an unqualified path lands in
tasks / runthe declared tasks; one of them, with its streams and exit code
batchseveral operations sent as one
doctorwhether this tool is wired into each client, and what goes round it
setupthe wiring, written — the one verb an assistant is not offered
servenothing — it becomes the MCP front end on stdio

src/Fettler/Edits.cs         11233  2026-08-12T08:05:52Z

Worked twins

# scripts/list-types.ps1
$out = fettle search "^public sealed" --glob "src/**/*.cs" --json
if ($LASTEXITCODE -ne 0) { throw "search failed: $out" }
$out
# scripts/list-types.sh
out=$(fettle search '^public sealed' --glob 'src/**/*.cs' --json) || {
  printf '%s\n' "$out" >&2; exit 1;
}
printf '%s\n' "$out"

In machine-readable mode the complete result — failures included — is on stdout. Windows PowerShell 5.1 turns a native program's redirected stderr into NativeCommandError records and sets $? false even on exit code 0, so any design needing 2>&1 to retrieve an answer is broken on the primary development platform.

9. What it can read

Fettler is the only reader on a machine where the assistant's own has been denied, so a type it cannot open is a file nobody can open.

TypeHow it comes back
Text, in any encoding a byte-order mark names, plus UTF-8lines, with the encoding, the line ending, whether the endings are mixed, and a hash
CSVas text — so a spreadsheet exported as CSV needs nothing special
Notebooks (.ipynb)cells, sources and outputs, rendered — not the JSON they are stored in
PDFtext, page by page, each page announced so a citation can name one
Images (png, jpg, gif, webp)mime type and dimensions from the header, without decoding a pixel; over MCP the bytes go as a native image part
Archives (.zip, .tar, .tar.gz, .tgz)the manifest — every member, its size, its date, and whether it carries the execute bit. --member NAME reads one entry out, decoded like any other file, without unpacking anything
A lone .gzwhatever is underneath it — one file wearing a coat
Anything else binaryrefused, saying so
  • read stops at 2000 lines unless --to says otherwise, and says how many are left. find stops at a thousand, search at two hundred.
  • --tail N is the end of the file, counted backwards, so reaching the end of a log or a build transcript needs neither its length nor any arithmetic. It is not combinable with --from/--to: the end of a file and a named range are two questions, and answering one of them by precedence is a confident wrong answer rather than an error.
  • A notebook's non-text output is measured rather than pasted — one output cell routinely holds a megabyte of base64 for a picture nobody can see.
  • Word and Excel are out of scope. Export as PDF and CSV, both of which this reads; an office-format parser is a permanent maintenance liability for a tool that edits source trees.
  • No plugins. A declared command needs an explicit execute grant; a plugin loader is arbitrary code execution, in process, at full trust, with no gate at all. A declared converter task is the honest form, and it already exists.

Unpacking one

extract ARCHIVE --into DIR writes; everything above only reads. An archive is a list of paths somebody else chose, which is exactly why the tool that already refuses a path outside a tree is the right one to unpack with.

$ fettle read fettle-2.3.0-win-x64.zip
79605839  2026-08-16 16:08  - fettle.exe
    2545  2026-08-16 14:09  - NOTICE
    1133  2026-07-30 04:52  - LICENSE
3 members, 79609517 bytes uncompressed

$ fettle extract fettle-2.3.0-win-x64.zip --into tools
extracted 3 members (79609517 bytes) from work:fettle-2.3.0-win-x64.zip into work:tools
  • Refused whole, or not at all. Every member is resolved through the boundary before a byte is written, so an archive that would escape or that lands anywhere it may not leaves nothing behind. A half-unpacked archive is the state nobody can see the shape of — the same reason edit is all-or-nothing.
  • Zip slip is refused by construction, not by a check bolted on. A member called ../../etc/passwd resolves outside every tree and comes back exit 4, exactly like a path somebody typed.
  • And a member that escapes only the destination is refused too. out/../elsewhere.txt normalises to somewhere the boundary is perfectly happy with, so the tree check passes and the file still lands nowhere near where you said. Nothing is wrong with the path; what is wrong is that it is not where you put it.
  • A link member is refused rather than skipped. Creating links is out of scope anyway, and a symbolic link inside a tar is the one member that can point out of the tree after every path check has passed. Skipping it silently would produce an extraction that looks complete and is not.
  • The executable bit is carried. R6.9 is this project's own clause about that bit, and its release depends on a fettle arriving out of a tar still able to run.
  • Bounded, not endured. A cap on member count and on total unpacked bytes, refused with a reason — the same posture as the bound on a runaway pattern. A compressed archive can name far more content than it occupies, and finding that out by running out of disk is finding out too late.
  • Nothing is overwritten without --overwrite, and an existing file is a refusal before anything is written rather than a surprise halfway through.
It reads archives and does not write them. Producing one is a build output, and building is what a declared task and run are for. And find/search deliberately do not reach inside an archive: that would make members into paths, and then the boundary has to answer what a scope means inside a container. Read the manifest, extract, search the tree — three honest steps beat one murky one.

10. Arguments it will not guess at

  • A flag no verb knows is refused, never ignored — one dash or two. A flag taking a value swallows the argument after it, so a misspelt --gob "*.cs" eats the pattern and the search then runs against the whole tree with complete confidence. A single dash is the same trap wearing one fewer character: search PATTERN -i, the spelling every grep in the world uses, would otherwise be read as a second pattern and answer the union of two questions. -e is the only short flag there is; a pattern or path that genuinely starts with a hyphen goes after a bare --, or through --pattern-file or --pattern-stdin.
  • A known flag with no value is refused too — the name was right and the value was missing. Write --NAME= for a deliberately empty one.
  • A pattern may arrive as bytes. --pattern-file and --pattern-stdin, one per line; likewise --replace-file, --with-file and --text-file, so text with quotes and newlines never has to be escaped onto a command line.
  • A leading byte-order mark on a stream is taken off, on the command line's streams and the MCP front end's alike. Windows PowerShell emits one whether asked to or not; keeping it made a pattern match nothing and spliced an invisible character into the middle of a source file. A mark further along is left alone.
  • Text an edit brings in is rewritten into the file's own line endings; text already there is untouched. A PowerShell here-string is CRLF whatever the file is, and splicing that in verbatim leaves a file disagreeing with itself by one line — which nothing notices until a version control system does.
  • A file that disagrees with itself says so. read marks it (MIXED) beside the dominant ending. Nothing is silently regularised.

11. What it touches besides content

ThingWhat Fettler does
The executable bitpreserved by copy and move, reported by read and find, settable by exec. The one permission git tracks, because it is the only one meaning the same thing on both platforms.
Attributes, alternate data streams, extended attributescarried across a staged write, or the answer names what could not be.
The Windows read-only attributeread and named in the refusal, never met as an obscure OS error. delete --force clears it explicitly.
Links and junctionsreported with their targets, never created — creating one on Windows needs Developer Mode or elevation.
Modified timereported; preserved on copy only when asked. Both branches explicit, because Windows carries the time across where POSIX cp gives a new one.
Everything else about permissionsnothing. POSIX modes and Windows ACLs do not map onto one another, and an abstraction over them would be a falsehood told in a table.

12. The rules a caller has to know

RuleWhat it is
Glob* stays within one path segment; ** matches any number of whole segments including none; ? is one character and does not cross a separator. Case-insensitive on every platform, so a pattern behaves identically everywhere.
Exclusions.git, bin, obj, artifacts and node_modules, by name, with the count reported; --include-generated turns it off. .gitignore is not honoured — implementing its rules subtly wrong hides files while appearing to work.
Attributes never decide matchinga dotfile and a Windows hidden file are ordinary files, matched normally and reported.
Regular expressions.NET's dialect, which is neither PCRE nor ripgrep's, under a bound — non-backtracking where the pattern allows, an explicit timeout where it does not.
Encodinga byte-order mark decides and is preserved; absent one, content that decodes as UTF-8 is UTF-8; anything else is binary and refused. No statistical guess, because a wrong guess corrupts a file on the way out.
Orderingresults are ordered before any limit, so a truncated result is the same truncation twice and says it was truncated.
What runs at oncereads run concurrently; mutations are serialized against each other; run holds neither lock.

13. Reference: exit codes

Callers chain on exit codes because PowerShell 5.1 has no &&. The machine-readable answer carries the same word as an outcome field.

CodeOutcomeMeaning
0okit worked
1—an unexpected internal fault
2invalidthe request did not make sense — an unknown flag, a missing value, a malformed configuration
3not-foundthe path, or the task, is not there
4outside-rootthe path is outside every declared tree
5target-existsthe destination is occupied and no overwrite was asked for
6stalethe file changed since it was read — the hash passed as --expect no longer matches
7conflictambiguous or overlapping edits
8refusedFettler declined, for a stated reason
9deniedthe operating system declined — a sandbox, a restricted account, a read-only attribute, a file another process holds open
10timed-outa task outran its timeout and was killed
11governedthe path names a file that says what this tool may do
12credentialthe write would have added a secret the file did not already carry
8 and 9 are deliberately different. Refused means Fettler declined; denied means the platform did, for an operation Fettler was perfectly willing to perform. Collapsing them sends a caller to debug a boundary that is working.
