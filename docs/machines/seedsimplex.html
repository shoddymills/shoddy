Summary

seedsimplex bridges simplex: LPPROBLEM and LPSOLVE. Per R4.16 there is no PROBLEM or SOLUTION cell at the keyboard: both are dicts, the same LIST-of-PAIR shape seeddict already established, so DGET "status" answers a solution's status and DGET "x" its variables without this seed naming a word for either. LPPROBLEM checks costs and rhs against the matrix's own shape before building anything, since Optimize is total over a well-formed problem and a mismatched one is exactly the malformed input this seed should refuse rather than hand onward.

Why It's Useful

Optimize is total over a well-formed problem — there is no Error anywhere in simplex.shoddy — so the only thing that can go wrong is the problem itself, and that is exactly what LPPROBLEM refuses to build: costs that do not match the matrix's columns, a right-hand side that does not match its rows. Everything past that point answers, whatever the numbers are, which is why a status of UNBOUNDED or INFEASIBLE is a value on the stack rather than the end of the session.

Reading an MPS file

An MPS file is how a linear program actually arrives — from a modelling tool, a textbook, a colleague — and a session that can only build a problem by typing its matrix out by hand is a session that cannot read the thing anybody would hand it. MPSLOAD and its four companions bridge mps, answering the same problem dict LPSOLVE reads.

This one needed a different kind of guarding from every other bridged word in the tree. Elsewhere a word is made safe by asking the machine's own question first: FINIRR checks the bracket FinIrr would abort on, ENGINTEGRATE checks the n EngIntegrate would abort on. mps cannot be guarded that way, and an earlier pass recorded exactly that as the reason to leave it out — its dozen aborts are scattered through a fold over the lines, and there is no one question to ask beforehand that answers "will this parse".

So the seed builds the missing counterpart. MpsWhy is a total reader: it walks the same lines, in the same sections, applying the same rules, and answers the first thing wrong as prose, or nothing at all. Only then is ParseMps called, on text now known to parse.

That is a second scanner, and the drift is the cost. If mps grows a section, this has to learn it or a file the parser now accepts is refused here. Two things hold them together: the tokenizer is not copied — Fields is mps's own word, called here — and every branch of the validator names the mps line it mirrors. It is still a cost, and the alternative was a word that ends a calculator session on a malformed file.

It also catches two faults mps does not have a check for at all. A ROWS line of one field is read past the end of by the parser. And Val is strtod: it answers 0 for anything it cannot read, so a COLUMNS or RHS field of prose parses silently as a zero coefficient — a different linear program, solved confidently. Every numeric field is checked with IsNumeric here, which is the question Val does not ask.

User's Guide

The supplement mix — minimize 5X + 7Y subject to 2X + Y ≥ 8 and X + 2Y ≥ 10 — read off disk from mills/simplex-from-mps/files/mix.mps and solved, then asked what its columns were called:

> "mills/simplex-from-mps/files/mix.mps" MPSLOAD
x: { ( "costs" { 5 7 } ) ( "a" 2x2 { { 2 1 } { 1 2 } } ) ( "rhs" { 8 10 } ) }
> LPSOLVE "cost" DGET
x: 38
> "mills/simplex-from-mps/files/mix.mps" MPSLOAD LPSOLVE "x" DGET
x: { 2 4 }

And what a malformed file gets, in place of an ended session:

?: MPS: BAD ROW SENSE Z — A ROW IS N, G, L OR E
?: MPS: A COLUMNS LINE HAS oops WHERE A NUMBER SHOULD BE
?: MPS: A MI BOUND LETS A VARIABLE GO NEGATIVE, AND EVERY VARIABLE HERE IS ZERO OR ABOVE
?: MPS: THIS FILE MARKS COLUMNS INTEGER — MPSMIP AND MPSMIPLOAD READ THAT, AND EVERY VARIABLE HERE IS CONTINUOUS
?: MPS: THERE IS NO OBJECTIVE (N) ROW

What the second scanner cost, once

The paragraph above says the drift is the price of a second scanner, and it came due. mps learned to read a BOUNDS section as the rows a bound actually is, and this validator had not: for a while the keyboard refused files the machine underneath could answer perfectly well. It knows them now — LO, UP, FX, BV and PL, with MI, FR and a negative UP still refused because they let a variable go negative — and it remembers the column names as it goes, because BndRows aborts on a bound naming a column COLUMNS never declared and that is a question you cannot ask without having listened.

Word Reference

WordDescription
LPPROBLEM ( costs a rhs -- problem )A linear program: minimize costs . x s.t. a x >= rhs, x >= 0. Refuses if costs or rhs do not match a's shape.
LPSOLVE ( problem -- solution )The optimum. status is OPTIMAL, UNBOUNDED, INFEASIBLE or MAXITER.
MPSPARSE ( text -- problem )MPS text as a problem, normalised to a x >= rhs. Refuses, naming the first line at fault, rather than reading a file it does not fully understand.
MPSPARSEZERO ( text -- problem )The same, forcing x >= 0 on every variable so a BOUNDS section is skipped instead of read as rows.
MPSLOAD ( path -- problem )Read an MPS file and parse it, the guarded way throughout.
MPSLOADZERO ( path -- problem )The same, forcing x >= 0 on every variable.
MPSNAMES ( text -- dict )What the problem's columns and rows were called: a dict with vars and cons. An E row appears as its NAME+ and NAME- pair, matching how it was split, and a bound as NAME.LO or NAME.UP. Reads the file the same way MPSPARSE does, so the labels always line up with the rows they label.
