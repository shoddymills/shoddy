halifax

A programmable RPN calculator on the runtime stack — mills/halifax

← tallyAll millsAll mills →

Summary

A calculator at a prompt. Numbers go on a stack of no fixed depth, words work on them, and everything you would want from a programmable calculator is there because it was already in the tree: unlimited UNDO and REDO, programs you define at the prompt and keep as readable text files, first-class lists, money exact at the cent, matrices that multiply with *, an adding-machine tape you can save, and a TRACE mode that shows the stack after every token.

bin/mill run mills/halifax/halifax.shoddy

Named after Halifax Piece Hall (1779) — the region's actual wool-trading floor, where merchants totted up the day's business by hand. It is a thin program over thick machines: cuttle is the stack, reckoner is the engine, and seven reckoner seeds are the vocabulary. What halifax adds is an assembled dictionary, a prompt, and the five words that name a file.

Why Every Feature Was Free

Nothing in the list above was built for the calculator. Each one is a property of the language showing through:

A Session

This is the contract, not an illustration: test.shoddy reproduces it byte for byte, and a single character of drift fails the suite.

shoddy halifax — RPN. Numbers go on the stack; words work on them.
WORDS lists, HELP <word> explains, TRACE follows, UNDO backs out, QUIT leaves.
[ empty ]

x: 35
> 2 DUP *
y: 35
x: 4
> DROP 1250.75 MONEY 3 MSPLIT
y: 35
x: { $416.92 $416.92 $416.91 }
> UNDO
y: 35

y: 35
x: { $416.92 $416.92 $416.91 }
> UNDO

> DEG 90 SIN

z: 35

[ depth 6 ]
t: 1
z: 7

Reading it downward: x is the top of the stack and sits nearest the prompt, which is why the rows print deepest first. An empty stack says [ empty ] rather than printing nothing. Past four levels the render stops naming them and counts them instead, because x y z t are the four names a stack machine has. The three money shares add back to exactly $1,250.75. And 1 0 / leaves the stack untouched — the 1 and the 0 it pushed are gone with the line, because the line is the transaction.

Defining Words

: NAME … ; at the prompt, and the word is in the dictionary beside the built-in ones. WORDS lists it, HELP explains it, VIEW prints it back, and SAVE writes it to a file you can read.

> : VAT DUP 0.2 * + ;
ok: VAT defined
[ empty ]
> 250 VAT
x: 300
> SAVE "mine.halifax"
saved 1 word

mine.halifax then contains exactly what you typed:

: VAT DUP 0.2 * + ;

Which is the whole of the file format. There is no serialization step and no metadata — a definition is its tokens, so saving it is writing them down and loading it is reading them back through the same evaluator that would have run them typed. A definition that names a word the dictionary has not got is refused when it is defined rather than when it is run, so a file that will not load says so before it has loaded any of it.

A user word takes exactly one cell

This is the one thing about programming this calculator that surprises people, and it is the engine's rule rather than the mill's. A definition has no arity to declare: its body runs on a fresh stack holding the single cell the word was applied to, and whatever it leaves is pushed back. So VAT above works, and a two-argument HYP written the obvious way does not — it would underflow reaching for a cell that is not its.

A second argument arrives through a register, which is the same mechanism that gets a value into a MAP program:

> 4 "B" STO
ok: B
[ empty ]
> : HYP DUP * "B" RCL DUP * + SQRT ;
ok: HYP defined
[ empty ]
> 3 HYP
x: 5

Banked before, recalled inside. The reason the rule exists is that token lists have no closures, and giving a user word the caller's whole stack would make every definition's behaviour depend on what happened to be underneath it when it was called.

TRACE

One line per token: the token, a marker, and the stack that token left. NOTRACE turns it off.

> TRACE
trace on
x: 300
> 250 VAT
  250        | 300 250
  VAT        » DUP 0.2 * +
    DUP      | 250 250
    0.2      | 250 250 0.2
    *        | 250 50
    +        | 300
  VAT        « 300 300
y: 300
x: 300
MarkerMeans
|the token ran; what follows is the stack it left
»a sub-evaluation is being entered; what follows is the tokens about to run
«it has returned; what follows is the caller's stack with the answer merged in

The indent is not decoration. A user word's body, a { … } literal and every pass of a combinator all run on a fresh stack, so the cells on an indented row are a different stack from the ones on the row above. Read the cascade above again with that in mind: VAT is applied with 300 250 on the caller's stack, and its body sees only the 250 — its own one cell. Printed flat, those rows would look like a stack that lost its lower half and then got it back.

Every sub-evaluation is announced, because they all pass through one place in the engine. A combinator emits one » per pass and a single « when it merges, so a MAP over three elements reads as three runs of one program:

> { 1 2 3 } [ 2 * ] MAP
  {          » 1 2 3
    1        | 1
    2        | 1 2
    3        | 1 2 3
  {          « { 1 2 3 }
  [          | { 1 2 3 } [ 2 * ]
  MAP        » 2 *
    2        | 1 2
    *        | 2
  MAP        » 2 *
    2        | 2 2
    *        | 4
  MAP        » 2 *
    2        | 3 2
    *        | 6
  MAP        « { 2 4 6 }
x: { 2 4 6 }

The { 1 2 3 } literal traces too, because it is a sub-evaluation like any other — three cells collected on a stack of their own and pushed back as one list. The [ 2 * ] gets an ordinary | row, being a push rather than a run.

The Tape

Every transaction is recorded as it was shown: the line you typed, whatever the calculator said, and the stack as it was rendered. It keeps the last 500 rows and drops the oldest. TAPE pushes the row count, CLEARTAPE throws it away, and TAPESAVE "file" writes it out verbatim — which is why a saved tape reads back as the session it was:

> 250 VAT
x: 300
> SAVE "mine.halifax"
saved 2 words
x: 300

It records refusals too. A tape that showed only the lines that worked would be a record of a session that did not happen.

Running It

From mills/halifax/ — the wrapper is ./build.sh, or ./build.ps1 on Windows, same subcommands:

CommandWhat it does
./build.sh runThe calculator, at a prompt.
./build.sh testThe headless suite. No terminal, no display, no network.
./build.sh demoFeeds files/demo.halifax to the prompt, ending on a traced cascade.
./build.sh buildWeaves the program into bin/.

The shell owns a few words rather than the dictionary, and each is the whole line:

WordWhat it does
SAVE "file"Writes the words you have defined, as : NAME … ; text.
LOAD "file"Reads such a file back. One bad line refuses the whole file.
TAPESAVE "file"Writes the tape, exactly as it was shown.
RESETStarts again: empty stack, no history, no tape, only the words you started with.
QUITLeaves. Nothing is saved for you.
EXITA second spelling of QUIT. Same effect, same refusal if it turns up mid-line.

They are still registered in the dictionary, for their metadata alone — so WORDS lists them under -- shell -- and HELP SAVE answers. A mill whose file words were invisible to the two words people explore with would have hidden a third of itself. Typed anywhere but as the whole line they refuse and say so, which is what 3 4 SAVE "x" gets.

Paths are relative to the directory you ran from. If a file called halifaxrc is there, it is loaded before the first prompt — a place to keep the words you always want. A missing halifaxrc is silence, not an error.

How It's Built

Two files, and the split is the reason the mill is testable at all:

FileWhat's in it
halifax-core.shoddyPure. Assembles the state from reckoner and its seven seeds, reads a typed line to work out whether the shell has any business in it, and produces the lines to show. Nothing here reads a file, writes one or prints.
halifax.shoddyThe shell: a prompt, four files, and nothing else. Every effect the mill performs is in this one file, and there are six of them.

The stack render belongs to the engine rather than to either file, and that is deliberate: the tape records the rendered rows, so a second render in the mill would let the tape and the screen disagree about what happened. What the core owns are the lines around the stack — the banner, the prompt, the tape pane — each written as a line-list producer, so the full-screen face planned for v2 can reuse them unchanged.

The loop is one self-recursive Def, which is worth knowing if you copy this shape. The compiler turns a self tail call into a jump and a mutual one into a call, so a loop written as HxLoop → HxTurn → HxLoop would grow the stack by a frame or two per line entered — fine for an afternoon, not fine for a redirected script of a hundred thousand lines. So QUIT is decided by a pure test before the turn rather than by the turn handing back a stop, and the price is tokenizing the line twice.

Every file word uses a guarded builtin — TryReadFile and TryWriteFile, never ReadFile or WriteFile — because an unwritable path is an ordinary thing to answer at a prompt and an aborted mill is not.

How It's Tested

test.shoddy Includes halifax-core.shoddy and not halifax.shoddy, so nothing in the suite can read or write a file even by accident. The centrepiece is the three sessions on this page, asserted whole rather than sampled: every line the mill would print, compared byte for byte, with the first differing row named on failure. A render that drifts is a docs page that lies, and there is no other way to notice.

Around that: the render's edges at depth four and five, the traced MAP cascade above, the one-cell rule refusing rather than reaching past its own element, the tape's rows and its 500-row cap, UNDO and REDO as inverses across several steps, and HxRead on every shape of line a shell word can be typed in.

Then the part that matters most. Nothing keyable aborts the mill, so the suite feeds it eighty-five lines of nonsense — every word with an empty stack, wrong cell kinds, unterminated strings and brackets, a definition of itself, a definition of a number, every shell word misused — and after each one asserts that 3 4 + still answers 7. Survival is proved by the next line and not by the error, because "it did not die" is the actual contract and only a subsequent line can show it.

What is left untested is the loop and the four file words, which are the shell's and are effects.
