Summary

pac-vt100 is Pac in a terminal: a 39×25 maze of walls, dots, and cherries, four ghosts, and nothing on screen that isn't a character. Eat every dot to win; a cherry makes the ghosts edible for a few seconds. There is no window and no scribbler — the screen is any VT100/ANSI terminal, painted with escape strings from the vt100 machine, and keys arrive through the InKey builtin, non-blocking and unechoed. WASD, the arrow keys, or the numeric keypad move; Q or Escape quits; the menu's C toggles colour — with it off, only cursor addressing is ever emitted, never a colour code, exactly as in the C original.

The Original

Pac-Man itself needs no introduction — Namco, 1980, the most recognizable maze in software. This mill is a rewrite of a compact C terminal rendition (the original C source is not redistributed here; see THIRD-PARTY-NOTICES.md): same board[25][39] maze, same ghost direction scheme, same colour-toggle menu. What changed in the crossing is the interesting part — the C original mutates one global board in place and free-runs its read loop, while the Shoddy version threads an immutable state record through a fixed-rate tick, so its timing constants are re-tuned rather than copied (the C original's EDIBLE_TIMEOUT 300 loop iterations become 80 engine ticks, and so on — the header of pac-core.shoddy shows the arithmetic).

Running It

bin/mill run mills/pac-vt100/pac.shoddy

or, from mills/pac-vt100/, use the wrapper — build.cmd on Windows, ./build.sh on Linux/macOS/WSL:

./build.sh          # run the game (also: ./build.sh run)
./build.sh test     # run the headless simulation smoke check

It wants a real ANSI-capable terminal at least 80×26 (Windows Terminal, or any Unix terminal, is fine). The game runs one tick per frame at 100 ms, paced by the clock machine.

How It's Built

The pure model is pac-core.shoddy: the maze, the state record, the per-tick simulation — ghost AI, timers, collisions, eating, winning and losing — and the input actions. Coordinates are 0-based cells, directions are the C original's scheme (0 none, 1 up, 2 right, 3 down, 4 left), and the board is an Array of 25 row Strings holding # walls, . dots, + cherries, and eaten spaces — PutCell returns a new board, nothing mutates. It contains no cursor addressing at all, so it runs headless and is unit-tested that way, twice over: by test.shoddy in the folder and by src/Shoddy.Tests/PacTests.cs in the golden suite.

The terminal half is pac.shoddy: painting, the menu, and the loop. Its one sly trick: Print appends a newline, so each frame is assembled into a single string that ends by parking the cursor at row 1 — the newline then lands harmlessly on row 2 and can never scroll the maze away. Every recursive branch of GameLoop, MenuWait, and WaitKey calls itself directly — genuine self tail calls, which the compiler turns into loops.

Why More Than One File

The C original is one file that mutates one global board inside one free-running read loop — simulation, drawing, and input interleaved line by line, which is exactly what makes such programs hard to test. The port cuts along the effect line instead: pac-core.shoddy is everything the game is — maze, state record, ghost AI, timers, collisions, input actions — and emits not one cursor movement; pac.shoddy is everything the game shows, and decides nothing.

That's why the core can be tested twice over — by test.shoddy in the folder and src/Shoddy.Tests/PacTests.cs in the golden suite — driving the simulation tick by tick with no terminal anywhere. It's also what made the timing retune honest: when the free-running loop's constants had to become fixed-rate tick counts, every change landed in the core where a test could hold it still, not in the paint code where it would only show up as feel.

The Machines It Uses

MachineWhy
seqIn the core: Any, All, Contains, and Flatten — the questions the simulation asks of the maze and the ghosts (any dot left? is a ghost on this cell?).
strIn the core: the board is 25 row Strings, and Replace does the row surgery — PutCell rebuilds a row around one changed cell instead of mutating it.
mathIn the core: RandInt and Pick are the ghosts' dice.
vt100Both directions of the terminal protocol — and the direction the core needs is the surprise: it uses EvalKey to classify raw InKey input, because arrow and keypad presses arrive as escape sequences and decoding them is part of the pure input model. The shell uses the emit side — cursor addressing and clearing. (The machine stops at attributes, so the ANSI colour codes live in the shell itself.)
clockIn the shell: SleepUntil paces the loop to one tick per 100 ms frame without drift.
