Shoddy Documentation

One-Time Machine Setup

Install the SDK, build the mill, set SHODDYLIB and PATH — once per machine, on Windows or macOS.

Nothing is needed beyond a terminal and a clone of the repo. Do this once; re-do only if the repo moves or the mill is rebuilt at a new path. When the four steps pass, wire up your editor next on the VS Code page, and keep the Toolchain page handy for everything the mill can do.

Platform note. Commands below are shown per platform. The Unix commands (./build.sh, bin/mill) work the same on Linux and WSL as on macOS. Windows uses build.cmd and bin\mill.exe.
WHY

Why this matters: how Include finds machines/

A program folder outside the repo should never need its own copy of machines/. The language’s own mechanism handles this: Include "seq.shoddy" (a bare filename) checks the including file’s own directory first, then falls back to the SHODDYLIB environment variable’s directory. Set SHODDYLIB once to the repo’s machines/ folder and any folder — anywhere on disk — can Include the standard library with no relative paths and no drift between copies.

The one thing to get right is where you set it: at the level the whole machine sees — a User (OS-level) environment variable on Windows, an export in your shell profile on macOS — not in any one program’s configuration. Set there, every consumer inherits it: new terminals, the build wrappers, and (after a restart) VS Code and its debugger, which spawn the mill without a shell — the VS Code page explains that wrinkle. Environment is snapshotted at process launch, so restart terminals and editors after setting it.

A1

Install the .NET 10 SDK

Check first — dotnet --version in a terminal. If it’s missing or older than 10, install from dotnet.microsoft.com/download, or:

Windows
winget install Microsoft.DotNet.SDK.10
macOS
brew install dotnet-sdk
A2

Build the mill

The mill is not committed; build it from the repo root, then verify. The verify run should print HELLO FROM SHODDY and a run of worked examples. (What the wrapper actually runs, and why it’s a folder publish, is on the Toolchain page.)

Windows
build.cmd build
bin\mill.exe run tst\examples.shoddy
macOS
./build.sh build
bin/mill run tst/examples.shoddy
A3

Set SHODDYLIB and PATH

Point SHODDYLIB at the repo’s machines/ folder, and put the repo’s bin on your PATH so mill works from any directory — both at the machine-wide level from the note above, not in any one program’s settings.

Windows

Set a User environment variable:

setx SHODDYLIB "C:\github\shoddy\machines"

For PATH, use System Properties → Environment Variables and append C:\github\shoddy\bin to your user Path (safer than setx, which rewrites the whole value).

macOS

Add two exports to your shell profile (adjust the path to where you cloned the repo):

echo 'export SHODDYLIB="$HOME/github/shoddy/machines"' >> ~/.zshrc
echo 'export PATH="$HOME/github/shoddy/bin:$PATH"' >> ~/.zshrc

If SHODDYLIB ever doesn’t take (see Troubleshooting), the fallback is launchctl setenv SHODDYLIB "$HOME/github/shoddy/machines", which lasts until logout.

Watch outOpen a new terminal afterward (or source ~/.zshrc) — environment variables are snapshotted at process launch, so already-open terminals don’t see them. The same applies to a running VS Code, which must be fully restarted — that story is on the VS Code page.
A4

Smoke-test the whole chain

From a new terminal, in a scratch folder outside the repo — this is the real test: it proves both variables took, and that a program folder anywhere on disk will work, not just files inside the source tree.

  1. Create C:\temp\shoddytest\check.shoddy (Windows) or ~/shoddytest/check.shoddy (macOS): 
    Include "stats.shoddy"

Def Main()
    Print(Sum({ 1, 2, 3 }))
  2. From that folder, run mill run check.shoddy — expect 6. A “not recognized” error means PATH didn’t take; unknown word: Sum or a “cannot open” error means SHODDYLIB didn’t.
  3. Delete the scratch folder once it passes — and if you use VS Code, repeat this check from the editor after wiring it up (the VS Code page has the two-button version).
FIX

Troubleshooting

Machine-level symptoms — the ones that come from environment and paths, not from your program. Editor-side symptoms (F5 fails but ▶ works, Dock launches, millPath) are in the VS Code page’s table.

SymptomLikely cause
dotnet not recognized The SDK isn’t installed, or the terminal predates the install — open a new one
mill not recognized PATH doesn’t include the repo’s bin, the terminal predates the change, or the mill was never built (step A2)
unknown word: Sum (or any library word), or “cannot open” on an Include SHODDYLIB not set, pointing somewhere other than the repo’s machines/, or the terminal predates the change
macOS: works in one terminal but not another The exports went into a profile that shell doesn’t read — keep them in ~/.zshrc (or ~/.zprofile for login shells)
