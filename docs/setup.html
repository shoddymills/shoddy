Shoddy Documentation

Setup

Install the runtime, install the extension. Two steps, once per machine, on Windows, macOS or Linux.

The packaged extension carries its own mill and the whole machine library, so there is nothing to clone, nothing to build, and no environment to set. Follow Track A and you are writing Shoddy in a few minutes. Track B builds the mill from source instead — take it only if you want to work on Shoddy itself, or want the mill on your command line without VS Code.

Which track? If you want to write programs in Shoddy, Track A is the whole story. If you want to change the language, you want Track B — and the Toolchain page after it.
WHY

Why this works: how Include finds machines/

A program folder should never need its own copy of machines/. Include "seq.shoddy" — a bare filename, no path — is resolved in three places, in order:

  1. beside the including file, so a program’s own pieces always win;
  2. the directory named by the SHODDYLIB environment variable, if you have set one;
  3. the machine library shipped with the mill that is running — machines/ beside the executable, then one level up beside its bin/.

That third rule is why nothing needs configuring. The mill inside the extension finds the machines staged beside it; a mill you build yourself finds the repo’s machines/ from bin/. Both work from any folder on disk, with an empty environment.

SHODDYLIB survives as the deliberate override — set it when you keep several checkouts and want a program pinned to one of them. It is no longer part of installing Shoddy, and if you set one, the editor steps aside and lets it win.

Track A — install the extension

A1

Install the .NET 10 runtime

The mill is a .NET program, so it needs the runtime — the runtime, not the much larger SDK. Check first with dotnet --list-runtimes; if nothing at version 10 appears, install from dotnet.microsoft.com, or:

Windows
winget install Microsoft.DotNet.Runtime.10
macOS
brew install --cask dotnet-runtime
A2

Install the extension

Download the latest .vsix from the latest release, then in VS Code: Extensions view → the ··· menu → Install from VSIX… → pick the file you downloaded. Reload when prompted.

Watch outThe package is not code-signed. Windows SmartScreen or a strict enterprise policy may object to an unsigned binary; the release publishes a SHA-256 checksum so you can verify the download instead. Nothing here phones home — the mill is a local compiler.
A3

Smoke-test it

In a scratch folder anywhere on disk — that is the real test, since it proves a program folder needs nothing of its own:

  1. Create check.shoddy: 
    Include "stats.shoddy"

Def Main()
    Print(Sum({ 1, 2, 3 }))
  2. Open the folder in VS Code and press the ▶ Run button (or ctrl+r) — expect 6.
  3. Press F5 on the same file: the perch stops on the first line. That proves the debugger half of the chain too — the VS Code page is the tour.

If step 2 reports unknown word: Sum or cannot open the include, see Troubleshooting below.

Track B — build from source

For working on the language, the mill, or the machines — and for having mill on your command line. Everything here is instead of Track A’s A1–A2, not in addition; a mill you build yourself takes precedence over the extension’s bundled copy whenever the repo is your open workspace.

B1

Install the .NET 10 SDK

Check with dotnet --version. If it’s missing or older than 10, install from dotnet.microsoft.com/download, or:

Windows
winget install Microsoft.DotNet.SDK.10
macOS
brew install dotnet-sdk
B2

Clone and build the mill

The mill is not committed; build it from the repo root. The verify run should print HELLO FROM SHODDY and a run of worked examples. (What the wrapper actually runs, and why it’s a folder publish, is on the Toolchain page.)

Windows
git clone https://github.com/shoddymills/shoddy
cd shoddy
build.cmd build
bin\mill.exe run tst\examples.shoddy
macOS
git clone https://github.com/shoddymills/shoddy
cd shoddy
./build.sh build
bin/mill run tst/examples.shoddy

That is the whole setup: bin/mill finds the repo’s machines/ one level up on its own, so bare includes work immediately with nothing set. build.cmd machines (./build.sh machines) compiles the library to machine DLLs up front; the mill builds any machine you use that is missing one anyway, since a machine is always used compiled.

B3

Put mill on your PATH Optional

Only so you can type mill instead of the full path to bin/mill.

Windows

System Properties → Environment Variables, and append C:\github\shoddy\bin to your user Path (safer than setx, which rewrites the whole value).

macOS
echo 'export PATH="$HOME/github/shoddy/bin:$PATH"' >> ~/.zshrc
Watch outOpen a new terminal afterward (or source ~/.zshrc) — environment variables are snapshotted at process launch, so already-open terminals don’t see them.
FIX

Troubleshooting

Machine-level symptoms — the ones that come from installs and paths, not from your program. Editor-side symptoms (F5 fails but ▶ works, millPath) are in the VS Code page’s table.

SymptomLikely cause
“The framework Microsoft.NETCore.App version 10 was not found” The .NET 10 runtime isn’t installed (step A1), or the terminal predates the install — open a new one
unknown word: Sum (or any library word), or “cannot open” on an Include A SHODDYLIB left over from an older install is pointing at a directory that no longer holds the machines — clear it, or point it at a real machines/ folder. With it unset, the mill finds its own
dotnet not recognized Neither runtime nor SDK is installed, or the terminal predates the install
mill not recognized (Track B) PATH doesn’t include the repo’s bin, the terminal predates the change, or the mill was never built (step B2)
macOS: works in one terminal but not another The export went into a profile that shell doesn’t read — keep it in ~/.zshrc (or ~/.zprofile for login shells)
