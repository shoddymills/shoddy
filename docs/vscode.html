Shoddy Documentation

VS Code

Useless Things Made Useful Through Skill — now with a Run button.

Everything about writing Shoddy in VS Code: installing the extension, pointing it at the mill, the tasks, native debugging (the perch), and the one environment wrinkle worth understanding. Assumes the mill is already built and SHODDYLIB is set — that's One-Time Machine Setup; do it first.

Only two sections here ask you to do anything: installing the extension (required, once) and the smoke test (recommended, a minute). Everything else is optional with its trigger stated on the section, plain usage (§3–§4, §6), or background (§5).

Key note. Shortcuts are written Cmd+… / Ctrl+… — macOS uses Cmd, Windows and Linux use Ctrl. Everything else on this page is identical on every platform.

1. Install the extension Required · once

The repo ships its own extension in vscode-shoddy/: real Shoddy highlighting (keywords, builtins, quotations, stack-effect signatures, Rem/' comments, all case-insensitive), block-aware indentation, snippets (def, select, fn, ...), native debugging with F5 (section 3), and mill commands — Shoddy: Run File (ctrl+r, plus the ▶ button), Weave File, Build Machine from File, and Show Generated C#.

The extension is plain JavaScript — no build step. A packaged vscode-shoddy-1.0.0.vsix ships in the folder; install it from the repo root (works on macOS, Windows, and Linux):

code --install-extension vscode-shoddy/vscode-shoddy-1.0.0.vsix

To rebuild it yourself, run ./build.sh vsix (build.cmd vsix on Windows).

Or in VS Code: Extensions view → ··· menu → Install from VSIX… → pick the file. Reload when prompted. (If code isn't on your PATH: on macOS press Cmd+Shift+P and run Shell Command: Install ‘code’ command in PATH once; the Windows installer adds it by default.)

Optional — only if you've edited the extension: repackage before installing (the committed .vsix may be stale):

npm install -g @vscode/vsce
cd vscode-shoddy && vsce package        # emits a fresh .vsix

Optional — only if you're developing the extension: to iterate without packaging at all, open the vscode-shoddy/ folder in VS Code and press F5 — that launches an Extension Development Host with it loaded.

2. Point it at the mill Optional

The extension finds the mill via the shoddy.millPath setting, falling back to the workspace's bin/mill (bin/mill.exe on Windows), then mill on your PATH. If Setup's step A3 put the repo's bin on your PATH, that last fallback already works everywhere and you can skip this section. Set millPath when one of these is true: you skipped the PATH step; you keep several checkouts and want the editor pinned to one of them regardless of PATH; or something else named mill shadows the real one.

If you do set it, set it in User settings, not per-workspace, so every folder you ever open — inside the repo or out — finds it with zero per-folder setup: Ctrl+Shift+P / Cmd+Shift+P → Preferences: Open User Settings (JSON), then add:

"shoddy.millPath": "C:\\github\\shoddy\\bin\\mill.exe"

(macOS/Linux: the full absolute path to bin/mill — don't rely on ~ expanding inside settings.)

The repo's .vscode/settings.json pins what matters either way: Shoddy's blocks are indentation-based (a tab counts as 4) and the whole corpus uses 4 spaces — let the editor keep it that way.

3. Debugging — the perch Usage · nothing to configure

Start here, because it's the fastest way to see the whole chain working and it needs zero configuration. Shoddy has native debugging (in mill-speak, the perch — where woven cloth was inspected for flaws). Open any .shoddy file and press F5: no launch.json needed. The program compiles with debug instrumentation and stops on its first line. Then:

  • Breakpoints — click in the gutter of any .shoddy file, including the machines' sources (the perch always splices sources, so you can step straight into Sum or MatMul).
  • Stepping — step over (F10), into (F11), out (Shift+F11). Stepping is source-line granular; a tail-recursive def loops in place without growing the stack, exactly as it executes.
  • Call Stack — your defs by name: UPDATEBINV ← SOLVE ← MAIN.
  • Variables — three scopes: Locals (the current def's bindings, shown as Shoddy values — records print as Person(Name = "ANN", Age = 34) and expand into fields), Globals (top-level Lets), and the Value Stack — half the story in a concatenative language.
  • Debug Console — type a binding's name to inspect it; hovering a name in the editor shows its value.

Limitation: Input reads end-of-file under the perch (interactive stdin isn't wired through the debug session) — debug the logic, run the interactive session with the run task from section 4.

4. Run, weave, build — inside VS Code Usage · nothing to configure

Open the repo (code /path/to/shoddy) and the shipped .vscode/tasks.json wires six tasks to the mill — they're committed, so there's nothing to set up:

Task What it does
Shoddy: run current file mill run on the file you're editing — bound to Cmd+Shift+B / Ctrl+Shift+B
Shoddy: weave current file compiles to a .dll beside the source (dotnet FILE.dll runs it)
Shoddy: build machine from current file compiles a machines/*.shoddy to Shoddy.Machines.<Name>.dll
Shoddy: show generated C# for current file prints what the weave emits — the readable compiler output
Shoddy: golden conformance tests dotnet test — the five goldens, the machines path, and the TCO check
Shoddy: rebuild mill into bin/ re-publishes the mill into bin/ (folder)

Workflow: open tst/examples.shoddy, press Cmd+Shift+B / Ctrl+Shift+B, and the program runs in the integrated terminal. Everything else is under Terminal → Run Task… (Cmd+Shift+P → “Run Task”).

Note the tasks are repo-local — in a folder outside the repo, use the extension's own ▶ Run button (or ctrl+r), which works everywhere.

Optional — only if you want a dedicated run key beyond Ctrl+Shift+B: add to your keybindings.json (Cmd+Shift+P → "Open Keyboard Shortcuts (JSON)"; on Windows use ctrl+r ctrl+r):

{
    "key": "cmd+r cmd+r",
    "command": "workbench.action.tasks.runTask",
    "args": "Shoddy: run current file",
    "when": "editorLangId == shoddy"
}

Building, without leaving the editor

Everything the mill builds can be built from in here — no terminal commands to remember:

  • Your program, to a .dll — with the file open, Terminal → Run Task… → Shoddy: weave current file. The assembly lands beside the source as FILE.dll, a self-contained program that later runs anywhere .NET runs. (Running it is a command-line affair — the Toolchain page — and one exception applies: scribbler-window programs only run under mill run, so weave console programs.)
  • A machine, to a library DLL — open a machines/*.shoddy and run Shoddy: build machine from current file; it compiles to Shoddy.Machines.<Name>.dll beside the source, which run and weave link against automatically from then on.
  • The mill itself — after touching anything under src/, run Shoddy: rebuild mill into bin/ to re-publish the toolchain, then Shoddy: golden conformance tests to prove it's still honest. Both are tasks; neither needs a terminal.
  • Curious what your program compiles to? — Shoddy: show generated C# for current file prints the weave's readable output.

5. How the extension sees your environment Background · no action

Nothing to configure here if you followed Setup — this section explains why Setup put SHODDYLIB where it did. Read it when F5 or Show Generated C# fails while ▶ Run works, or when you're tempted to set environment in workspace settings.

The extension invokes mill five different ways — Run, Weave, Machine, Show Generated C#, and F5 Debug — and they don't all inherit environment identically. Run/Weave/Machine go through VS Code's integrated terminal (which inherits terminal.integrated.env.* from workspace settings); Show Generated C# and F5 Debug spawn the process directly from the extension host, which inherits only the environment the VS Code process itself was launched with.

The practical consequence is about SHODDYLIB: setting it in a workspace's terminal.integrated.env would make Run work while silently breaking F5 debugging on the first Include-using program. So set it where the VS Code process will see it — a User environment variable on Windows, a shell-profile export on macOS (VS Code resolves your login-shell environment at launch, Dock launches included) — which is exactly what Setup has you do. And restart VS Code fully after setting it (macOS: Cmd+Q, relaunch): environment is snapshotted at process launch.

6. Interactive programs Usage · nothing to configure

Tasks run in the integrated terminal, so programs that use Input just work — run tst/gradebook.shoddy with Cmd+Shift+B / Ctrl+Shift+B and type at the prompts. To replay its scripted session instead (a command-line affair — the only one on this page):

bin/mill run tst/gradebook.shoddy < tst/golden/gradebook.in

7. Smoke-test the whole chain Recommended · once

Do this once after installing the extension — and again whenever SHODDYLIB or millPath changes, or the mill is rebuilt at a new path. From a scratch folder outside the repo — the real test: it proves a program folder anywhere on disk will work, not just files inside the source tree.

  1. Create check.shoddy in a scratch folder: 
    Include "stats.shoddy"

Def Main()
    Print(Sum({ 1, 2, 3 }))
  2. Open the folder in VS Code and run it with the ▶ Run button — expect 6, not unknown word: Sum or a “cannot open” error. (Ctrl+Shift+B won't exist out here — the tasks are repo-local.)
  3. Press F5 on the same file and confirm it also runs clean under the debugger — this is the step that catches the terminal-vs-extension-host environment gap from section 5, before it surprises you mid-program.
  4. Delete the scratch folder once both pass.

8. Troubleshooting As needed

Editor-side symptoms. If the command line is broken too, start with Setup's troubleshooting instead — fix the machine before the editor.

SymptomLikely cause
Works on ▶ (Run) but fails only on F5 or “Show Generated C#” SHODDYLIB was set only in a workspace's terminal.integrated.env, not where the VS Code process sees it — section 5
unknown word: Sum (or any library word) on Run and F5 alike SHODDYLIB not set, or VS Code wasn't restarted after setting it (Windows: after setx; macOS: after editing ~/.zshrc — fully quit with Cmd+Q)
macOS: works when VS Code is launched from a terminal (code .) but not from the Dock The login-shell environment wasn't resolved — make sure the export is in ~/.zshrc or ~/.zprofile and fully relaunch; as a fallback, run launchctl setenv SHODDYLIB … and relaunch (re-run after each login)
Mill not found at all None of the three lookups reached it: shoddy.millPath is unset or wrong (check it's in User settings, not lost in a workspace override, pointing at bin\mill.exe / bin/mill), the workspace isn't the repo, and the repo's bin isn't on the PATH the VS Code process inherited — if you just did Setup's A3, restart VS Code
Ctrl+Shift+B does nothing outside the repo Expected — the six tasks live in the repo's .vscode/tasks.json. Use the ▶ Run button or ctrl+r, which the extension provides everywhere
