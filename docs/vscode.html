Shoddy Documentation

VS Code

Highlighting, snippets, debugging and mill commands, with a Run button

This page covers everything about writing Shoddy in VS Code: installing the extension, the tasks, native debugging (the perch, Shoddy's debugger), and the one environment detail worth understanding. An extension is an add-on package that teaches VS Code something new; here, a whole language. This one carries its own mill (the program that compiles and runs Shoddy) and machines, so the only prerequisite is the .NET 10 runtime: Setup, Track A, two steps.

Only two sections here ask you to do anything: installing the extension (required, once) and the smoke test (recommended, a minute). Everything else is either optional, with its trigger stated on the section, plain usage (§3 to §4, §6), or background (§5).

Key note. Shortcuts are written Cmd+… / Ctrl+…: macOS uses Cmd, Windows and Linux use Ctrl. Everything else on this page is identical on every platform.

1. Install the extension Required · once

Shoddy has its own extension, and it provides:

  • real highlighting: coloring each kind of word so a program reads at a glance (keywords, builtins, quotations, stack-effect signatures, Rem/' comments, all case-insensitive);
  • block-aware indentation;
  • snippets: ready-made templates you fill in (def, select, fn, ...);
  • native debugging with F5 (section 3);
  • mill commands: Shoddy: Run File (ctrl+r, plus the ▶ button), Weave File, Build Machine from File, and Show Generated C#.

It also carries a complete toolchain, every tool needed to build and run Shoddy. A mill and every machine ship inside the package, so installing it is the whole install. Download the latest .vsix from the latest release (one package, every platform), then in VS Code: Extensions view → ··· menu → Install from VSIX… → pick the file you downloaded. Reload when prompted.

The bundled mill is portable .NET: mill.exe on Windows, and dotnet mill.dll everywhere else, through the runtime Setup had you install. The machines travel with it. That is why a bare Include "seq.shoddy" resolves in any folder you open, with nothing set.

Optional, only if you have edited the extension: repackage from the repo root, which stages a fresh mill and freshly built machines into the package first:

./build.sh vsix          # ./build.ps1 vsix on Windows

Optional, only if you are developing the extension: to iterate without packaging at all, open the vscode-shoddy/ folder in VS Code and press F5. That launches an Extension Development Host, a second VS Code window with your edited extension loaded.

Tip If GitHub Copilot is in this window too, spend five more minutes on Grounding an Assistant. Copilot has never read a line of Shoddy and will write you BASIC unless a .github/copilot-instructions.md tells it otherwise. That page has the file to copy.

2. Point it at the mill Optional

The extension looks for a mill in four places, in order: the shoddy.millPath setting; bin/mill inside your workspace, the folder you have open (bin/mill.exe on Windows); its own bundled copy; then mill on your PATH, the list of folders your terminal searches for commands. The bundled copy means almost everyone can skip this section.

The one ordering to know: a workspace's own bin/mill beats the bundled one. That is deliberate. When the repo is your open folder, the mill you just built is the one you want tested, not the one that shipped. Set millPath explicitly in two cases: you keep several checkouts (separate copies of the repository) and want the editor pinned to one regardless of which is open, or something else named mill hides the real one.

If you do set it, set it in User settings, not per-workspace. Then every folder you ever open, inside the repo or out, finds it with no per-folder setup: Ctrl+Shift+P / Cmd+Shift+P → Preferences: Open User Settings (JSON), then add:

"shoddy.millPath": "C:\\github\\shoddy\\bin\\mill.exe"

(macOS/Linux: the full absolute path to bin/mill. Do not rely on ~ expanding inside settings.)

The repo's .vscode/settings.json pins what matters either way: Shoddy's blocks are indentation-based (a tab counts as 4) and the whole corpus uses 4 spaces. Let the editor keep it that way.

3. Debugging: the perch Usage · nothing to configure

Start here: it is the fastest way to see the whole chain working, and it needs no configuration. Shoddy has native debugging: running your program one line at a time while you watch what it does. In mill vocabulary the debugger is the perch, the place where woven cloth was inspected for flaws. Open any .shoddy file and press F5: no launch.json needed. The program compiles with debug instrumentation (the extra bookkeeping that lets the debugger watch each line). It is the same program mill run builds, machines and all, and it stops on its first line. If it would not compile, the launch fails with the error the runner gives, rather than starting and dying part-way through.

The program runs exactly as it does under mill run. It gets a terminal panel of its own, named shoddy debug: FILE: it reads that terminal's keyboard (Input, InputLine, InKey), draws on its screen (escape codes and all, so VT100 games play), opens scribbler windows and plays sound. It runs from its own folder, whichever folder the workspace is opened on, so a relative path such as files/words.txt finds the file beside the program. That is true in a checkout and out of one: the machines the extension ships are debugged the same way as the ones in the repository. Then:

  • Breakpoints: a breakpoint pauses the program at a line you mark. Click in the gutter (the margin left of the code) of any .shoddy file: your own, or a machine's. A machine is Shoddy too, and the debugger runs every machine your program reaches in its instrumented build, so a breakpoint in seq.shoddy stops there. A top-level Let is a line like any other. A line stops once each time it runs, however much happens on it.
    • Conditional: right-click the breakpoint, Edit Breakpoint… → Expression, and give any Shoddy expression that answers True or False, such as n = 3. A condition that fails, or answers something else, stops the program and says why in the Debug Console.
    • Hit count (Edit Breakpoint… → Hit Count): a whole number stops on that hit only. >, >=, <, <= or = before it compare, and % N stops on every Nth hit. Only hits whose condition held are counted.
    • Logpoint (right-click the gutter, Add Logpoint…): a message that is written to the Debug Console each time the line runs, without stopping. Anything in braces is evaluated: n is {n}, doubled {n * 2}.
  • Runtime errors stop the program at the failing line, with every frame, local and stack value still there to look at; the Debug Console shows the message. Continue, and the program ends with the error exactly as it would under mill run. Untick Runtime errors in the Breakpoints view to let errors end the program without stopping.
  • Pause (F6) stops a running program at the next line it reaches, a program stuck in a loop included.
  • Stepping: run one line at a time: step over (F10), into (F11), out (Shift+F11). Step into goes into the Def a line calls, a machine's included, so you can watch Sum or MatMul work. A tail-recursive def (one whose last act is to call itself) loops in place without growing the stack, exactly as it executes, and each pass is a new line to step to.
  • Call Stack: the chain of defs that called each other, by name: UPDATEBINV ← SOLVE ← MAIN.
  • Variables: three scopes: Locals (the current def's bindings, shown as Shoddy values; records print as Person(Name = "ANN", Age = 34) and expand into fields), Globals (top-level Lets), and the Value Stack, half the story in a stack language. Double-click any of them, a record's field or a list's element included, to set it to the value of any Shoddy expression. The program computes with the new value from the next thing it does.
  • Debug Console, Watch and hover: any Shoddy expression, evaluated in the frame you are looking at. It can use the frame's locals, the top-level Lets, the program's own Defs and types, every machine word the program included, and the builtins: Twice(k) + Px(p), IndexOf(names, "ANN"). It is compiled, as everything in Shoddy is, and it leaves the program as it found it.

Settings for a launch

None are needed. To give a program arguments, arm the network, or run it from another folder, add a launch.json (Run → Add Configuration… → Shoddy) and set any of these:

SettingWhat it does
programThe .shoddy file to debug. Default: the one you are editing.
argsThe program's arguments, what Args() answers: ["words.txt", "42"] is mill run FILE words.txt 42.
allowNettrue arms the network, as mill run --allow-net does.
cwdThe folder the program runs from. Default: the program's own folder. A relative one is taken against the workspace folder.
console"integratedTerminal", the default: a terminal of its own, with keyboard and screen. "internalConsole": output to the Debug Console instead, with no keyboard, so Input reads end of input.
stopOnEntryStop on the first line.
{
    "type": "shoddy",
    "request": "launch",
    "name": "Burler, seeded",
    "program": "${workspaceFolder}/burler.shoddy",
    "args": ["files/words.txt", "42"]
}

The extension's Run, Weave, Build Machine and Show Generated C# commands run from the program's folder too.

4. Run, weave, build inside VS Code Usage · nothing to configure

Open the repo (code /path/to/shoddy) and the shipped .vscode/tasks.json wires six tasks to the mill. They are committed, so there is nothing to set up:

Task What it does
Shoddy: run current file mill run on the file you are editing, bound to Cmd+Shift+B / Ctrl+Shift+B
Shoddy: weave current file compiles to a .dll beside the source (dotnet FILE.dll runs it)
Shoddy: build machine from current file compiles a machines/*.shoddy to Shoddy.Machines.<Name>.dll
Shoddy: show generated C# for current file prints what the weave emits: the readable compiler output
Shoddy: golden conformance tests dotnet test: the five goldens, the machines path, and the TCO check
Shoddy: rebuild mill into bin/ re-publishes the mill into bin/ (folder)

Workflow: open tst/examples.shoddy, press Cmd+Shift+B / Ctrl+Shift+B, and the program runs in the integrated terminal (the terminal panel inside the editor). Everything else is under Terminal → Run Task… (Cmd+Shift+P → “Run Task”).

Note the tasks are repo-local. In a folder outside the repo, use the extension's own ▶ Run button (or ctrl+r), which works everywhere.

Optional, only if you want a dedicated run key beyond Ctrl+Shift+B: add to your keybindings.json (Cmd+Shift+P → "Open Keyboard Shortcuts (JSON)"; on Windows use ctrl+r ctrl+r):

{
    "key": "cmd+r cmd+r",
    "command": "workbench.action.tasks.runTask",
    "args": "Shoddy: run current file",
    "when": "editorLangId == shoddy"
}

Building, without leaving the editor

Everything the mill builds can be built from in here, with no terminal commands to remember:

  • Your program, to a .dll: with the file open, Terminal → Run Task… → Shoddy: weave current file. The assembly lands beside the source as FILE.dll, a self-contained program that later runs anywhere .NET runs. (Running it is a command-line matter; see the Toolchain page. One exception applies: scribbler-window programs only run under mill run, so weave console programs.)
  • A machine, to a library DLL: open a machines/*.shoddy and run Shoddy: build machine from current file. It compiles to Shoddy.Machines.<Name>.dll beside the source, which run and weave link against automatically from then on.
  • The mill itself: after touching anything under src/, run Shoddy: rebuild mill into bin/ to re-publish the toolchain, then Shoddy: golden conformance tests to prove it still passes. Both are tasks. Neither needs a terminal.
  • Curious what your program compiles to? Shoddy: show generated C# for current file prints the weave's readable output.

5. How the extension sees your environment Background · no action

Nothing to configure here. This section explains what the extension does with SHODDYLIB on your behalf, and matters only if you decide to set one yourself.

The extension invokes mill five different ways (Run, Weave, Machine, Show Generated C#, and F5 Debug), and they do not all receive environment variables the same way. (An environment variable is a named setting the operating system hands to a program when it starts.) Run, Weave and Machine go through VS Code's integrated terminal, which picks up terminal.integrated.env.* from workspace settings. Show Generated C# and F5 Debug spawn the process directly from the extension host (the background process that runs extensions). Those two inherit only the environment the VS Code process itself was launched with. That split used to be a trap: a SHODDYLIB set in workspace settings made ▶ Run work while silently breaking F5 on the first Include-using program.

The extension now closes that gap itself. It points SHODDYLIB at its own bundled machines by both routes at once (a terminal environment collection for the terminal commands, and an explicit environment for the two processes it spawns), so all five behave identically with no setup.

If you set SHODDYLIB yourself, the extension uses yours everywhere. Set it where the VS Code process will see it: a User environment variable on Windows, a shell-profile export on macOS (VS Code resolves your login-shell environment at launch, Dock launches included). Then restart VS Code fully (macOS: Cmd+Q, relaunch), because a program copies its environment variables once, at launch. Setting it in a workspace's terminal.integrated.env reopens exactly the split described above, so do not.

One other environment variable the mill reads: SHODDY_LINT, set to anything, turns on the weave-time accessor-shadowing warning. The same launch rules apply: set it where the VS Code process will see it if you want F5 and ▶ Run to lint alike. What it warns about, and why it is off by default, is on the Toolchain page.

6. Interactive programs Usage · nothing to configure

Tasks run in the integrated terminal, so programs that use Input work as they are, and so does F5: the debugged program has a terminal of its own (section 3). Run tst/gradebook.shoddy with Cmd+Shift+B / Ctrl+Shift+B and type at the prompts. To replay its scripted session instead (a command-line matter, the only one on this page):

bin/mill run tst/gradebook.shoddy < tst/golden/gradebook.in

7. Smoke-test the whole chain Recommended · once

Do this once after installing the extension, and again whenever SHODDYLIB or millPath changes, or a mill you build yourself moves. Use a scratch folder outside any checkout. That is the real test: it proves a program folder anywhere on disk will work, not just files inside the source tree.

  1. Create check.shoddy in a scratch folder: 
    Include "stats.shoddy"

Def Main()
    Print(Sum({ 1, 2, 3 }))
  2. Open the folder in VS Code and run it with the ▶ Run button. Expect 6, not unknown word: Sum or a “cannot open” error. (Ctrl+Shift+B will not exist out here. The tasks are repo-local.)
  3. Press F5 on the same file and confirm it also runs clean under the debugger. This is the step that catches the terminal-vs-extension-host environment gap from section 5, before it surprises you mid-program.
  4. Delete the scratch folder once both pass.

8. Troubleshooting As needed

Editor-side symptoms. If the command line is broken too, start with Setup's troubleshooting instead. Fix the machine before the editor.

SymptomLikely cause
Works on ▶ (Run) but fails only on F5 or “Show Generated C#” A SHODDYLIB of your own was set only in a workspace's terminal.integrated.env, where the two spawned processes never see it. See section 5
unknown word: Sum (or any library word) on Run and F5 alike A SHODDYLIB left over from an older install points somewhere that no longer holds the machines. It overrides the bundled ones. Clear it and fully restart VS Code (macOS: Cmd+Q). With it unset the extension supplies its own
macOS: works when VS Code is launched from a terminal (code .) but not from the Dock Only possible with a SHODDYLIB or PATH of your own: the login-shell environment was not resolved. Keep the export in ~/.zshrc or ~/.zprofile and fully relaunch, or drop it and let the bundled toolchain answer, which no Dock launch can miss
“The framework Microsoft.NETCore.App version 10 was not found” The .NET 10 runtime is not installed, or VS Code predates the install. Setup step A1, then restart VS Code
Mill not found at all All four lookups missed, which normally means the package was built without its mill staged. Check shoddy.millPath is not set to a stale path (it is checked first, and a wrong value beats the bundled copy), then reinstall the .vsix from the Releases page
Ctrl+Shift+B does nothing outside the repo Expected: the six tasks live in the repo's .vscode/tasks.json. Use the ▶ Run button or ctrl+r, which the extension provides everywhere
