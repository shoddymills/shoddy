A machine now exports the words it declares, and not the ones it includes.
That will break programs. Read the first section before you upgrade — the
compiler tells you exactly what to add, and the fix is one line per case.

## Breaking

- **A machine's includes are no longer part of its surface.** Including
  `stats.shoddy` used to hand you `seq` and `dict` as well, bare, because
  everything landed in one flat table. It no longer does. A program that
  calls `ZipWith` after including only `stats` will not compile:

  ```
  unknown word: ZIPWITH — declared in seq.shoddy, which stats.shoddy
  includes but does not export. Add: Include "seq.shoddy"
  ```

  **The fix is the message.** Add the include it names; the dependency was
  already compiled and linked, so nothing else changes. Ten files in this
  repository needed one, and the compiler found every one of them — the
  audit that preceded it had predicted six.

  The same refusal reaches patterns, where a missing type reads as a syntax
  error rather than an unknown word. `Case Pair(a, b)` after including only
  `dict` now says `malformed CASE — Pair is declared in seq.shoddy …`
  rather than complaining about the syntax of a line whose syntax is fine.

  Why: a surface you could not read off a file made every machine's
  contract guesswork, and made adding a word to `seq` a possible collision
  in every program in the tree. Now `Include` is a statement about what a
  file uses. One consequence is worth having on its own — exactly one pair
  of machines in the whole library still shares a word (`net` and `turtle`,
  over `Close`), so a namespace is something you reach for when you include
  both, not a habit.

- **`As` covers the file you named, and nothing further.** It used to
  propagate down the whole include chain, so `Include "net.shoddy" As Sock`
  renamed `str`'s `Join` to `SockJoin` as well. It no longer does. This
  also means a file's spelling cannot change because one of its
  dependencies added an include. `docs/spec.html` §13.1 documented the old
  rule; it was describing one of two behaviours the compiler had, since the
  compiled path never did this.

- **A machine is always used compiled.** An `Include` that resolves into a
  machine library builds that machine if it has no DLL, rather than
  splicing the source. Splicing put a machine's own includes into the
  caller's table, so whether a program was legal depended on what happened
  to have been built. Your own source files are unaffected: they splice as
  they always have, which is what lets a mill spread itself across a dozen
  files.

- **The debugger compiles the program the runner compiles.** It used to
  splice every machine, so none of the above applied under it and a program
  the runner refused would launch and run. Two consequences: a breakpoint
  set in a machine's source comes back unverified — there are no
  instrumented lines in a DLL to stop on, and you step *over* a machine
  word as you would over any other runtime — and a program that will not
  compile now fails at launch with the runner's error rather than starting
  and dying part-way through.

## Fixed

- **A machine's exported surface no longer depends on its build state.**
  `mill machine` could emit two different DLLs from identical source: with
  a dependency spliced, its words joined the machine's manifest under
  whatever namespace the include carried; with the same dependency
  compiled, they became external references and were exported by nobody.
  A contributor's local build could differ from CI's with nothing in the
  source to explain it.

- **Resolving a machine and recording its namespace are one call.** They
  were two separate optional callbacks, and wiring only the first discarded
  the `As` in silence — no warning, no error, and every collision it
  existed to prevent came back.

- **A scoped-out word is refused at compile time wherever it appears.** The
  linter reports only what it can model, so an unknown word inside a
  quotation of unknown effect used to reach code generation unmentioned and
  take the program down mid-run. It is now a weave error, because this is
  the one unknown word that is neither a typo nor a name that might turn up
  at runtime.

- **A freshly installed extension no longer rebuilds its own machines.**
  Staging stamped each DLL as it copied, alphabetically, and a machine
  counts as stale when a DLL it depends on is newer than its own — so `csv`
  (behind `dict`, `seq` and `str`) arrived stale and rebuilt itself on first
  use, writing into the install directory.

## Added

- **`warning: Include "X.shoddy" — no word or type from it is used`.** Now
  that an include is a declared interface rather than an incidental splice,
  one that earns nothing is noise, and it is how a re-export habit starts.
  Warning only; an unused include is untidy, never wrong. It found five on
  its first run, including one the compiler's own source had noticed years
  earlier and called "a pure re-export Include".

- **`verify-docs.js` reads the machine catalogue in `spec.html`.** Each
  bullet states what that machine includes, and nothing checked it: two
  trailers were false and nine more stale while the docs gate reported
  green. It is ground truth now, like the machine pages.

## Documentation

`spec.html` §13 opens with the distinction — a machine is a boundary, a
program's own files are one program — and §13.1 states the namespace rule
positively. `errors.html` gains the two new refusals and the new warning,
each with a worked before-and-after. `vscode.html` says what a compiled
runtime means for a debugger. `quickref.html`, `setup.html`, `build.html`,
four mill pages and both AI grounding blocks follow.
