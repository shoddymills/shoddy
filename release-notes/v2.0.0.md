Shoddy programs can now be hosted: from .NET, and from a real app.
The 2 signals the new surface — nothing in the language changed, and
every existing program runs as it did.

## Added — hosting Shoddy from .NET

- **`Shoddy.Hosting`** — call a woven mill's words from C#, F# or VB as
  ordinary methods (`Mode N`), or run a whole console mill through
  pipes (`Mode T`, `RunWovenAsync`). Values cross the boundary as
  `ShoddyValue`; records round-trip intact.
- **`Shoddy.Build`** — MSBuild targets (`ShoddyWeave`) that verify,
  gate, weave and reference your mills during `dotnet build`. Declare a
  mill and its grants in the csproj; the woven DLLs are ordinary build
  inputs.
- **`mill manifest`** — every mill can carry a `mill.manifest`: its
  machine closure (generated) and its capability declarations
  (hand-written, schema-checked). Grants are default-deny: a required
  capability your project has not granted refuses the build with the
  exact line to add.
- **Capability tags and lint** — every machine in the library declares
  the capability its words need; the lint warns on a mill using a
  capability its manifest does not declare.
- **`Shoddy.Mill.Headless`** — the pure toolchain verbs (`weave`,
  `machine`, `manifest`, `gen`, `lex`) with no window or audio stack:
  weaves in a bare container, refuses `run` by name. Byte-identical
  output to the desktop mill for every shared verb.
- **Debugging a hosted mill** — debug builds weave an instrumented core
  and carry a Perch attach service; F5 in a scaffolded project attaches
  the .NET debugger and the Shoddy debugger together. Release builds
  provably carry neither.
- **Templates** — `dotnet new shoddy-console` and `dotnet new
  shoddy-lib` scaffold a working host around any mill.
- **Proof projects** (`proofs/`) — C# and F# consumers, the refusal and
  degraded builds, and the dependency floor, all run in CI.

## Added — Shoddy Reckoner (Windows)

- **`hosts/maui/shoddy-reckoner`** — the Halifax calculator as a MAUI
  app: a terminal-like transcript face over the same core the terminal
  mill runs, proven against the terminal's own transcript. Definitions
  span entries, `halifaxrc` persists across launches in app storage,
  and every seeded capability is supplied for real — files under the
  app's own root, plotter and turtle drawings on an in-app canvas,
  the buzzer complete on a Windows audio sink, `NETGET` on a worker
  with a busy state and cancel.
- The Windows lane builds and tests today; Mac Catalyst, iOS and
  Android are staged next on their own workstation, and no store
  submission is part of this release.

## Changed

- `mills/halifax` now ships a `mill.manifest` declaring its full
  capability surface (the lint found it also needed `vt100` — it did).
- Buzzer synthesis and the channel engine moved from the desktop mill
  into the shared runtime behind an audio-sink seam; desktop audio is
  unchanged and every host sounds the same because the engine, not the
  sink, decides behaviour.
- Woven build outputs in mill folders (`mills/**/*.dll`,
  `*.runtimeconfig.json`) are now gitignored: they are build results
  the proof suite regenerates.

## Fixed

- `mill machine` on a hyphenated core (`halifax-core.shoddy`) produced
  an invalid class name and could not weave; the DLL keeps its
  hyphenated name and the class is sanitized, read from the manifest.
- The weave was not deterministic — two identical builds emitted
  different bytes. It is now: same inputs, same bytes, asserted by
  test.
- A woven core DLL sitting beside a mill could hijack the mill's own
  `Include` resolution; a program's own siblings now always splice.
